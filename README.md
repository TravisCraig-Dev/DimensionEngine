# Dimension Engine

A 2D/3D game engine written in C++23 on **Vulkan 1.3**. Its core is a custom **Entity Component System**, and it ships with a Unity-style **editor** and a standalone **player** runtime.

```
Engine/    DimensionEngine.dll (ECS, renderer, scene, physics, audio, assets, UI, ImGui)
Editor/    DimensionEditor: docking editor (Hierarchy, Inspector, Scene/Game views, Project, Console)
Player/    DimensionPlayer: runs a project's start scene without the editor (used for builds)
Game/      SandboxGame.dll: gameplay scripts and systems, hot-reloaded by the Editor, loaded by the Player
Tests/     DimensionTests: headless tests for the ECS, scenes, serialization, scripts, physics, audio and more (pass a name filter as the first argument)
Projects/  Sandbox sample project (Demo3D and Demo2D scenes)
```

## Features

**Core and ECS**
- Sparse-set ECS with generational entity handles and typed views (`for (auto [e, t, s] : reg.ViewOf<Transform, Sprite>())`).
- Deep registry cloning that preserves entity handles, which powers Play mode.
- Reflection for components and script fields. The inspector, serializer and prefabs are all driven by one field declaration.
- An ECS `System` interface with a registry. Gameplay scripts can be written in C++ (`ScriptableEntity`) or **C#** (`Behaviour`), and both hot-reload in the editor.
- **C# editor extensions** (like Unity's `UnityEditor`): in the scripts assembly, a static method with `[MenuItem("Tools/Do Something")]` becomes a menu command (its first path part is the menu, an existing one such as Window gains the item), and a class deriving from `EditorWindow` with `[EditorWindow("Title", "Window/Title")]` a dockable window drawn by its `OnGUI` with `EditorGUI` (labels, buttons, toggles, number, slider, vector, color and text fields, separators). `Selection` (the active and all selected objects), `Undo.Record` (one undo step, the scene marked changed) and `EditorScene.CreateEntity` reach the scene being edited; they register when the scripts load and reload with them, and never run in a built game. The Sandbox's `SceneTools.cs` adds Tools > Line Up Selected and Add Marker, and Window > Scene Tools. `--menu "Tools/..."` runs one on startup, `--open "Title"` opens a window.
- **C# custom Inspectors** (like Unity's `CustomEditor`): a class deriving from `Inspector` with `[CustomInspector(typeof(MyScript))]` draws that script's Inspector in its `OnInspectorGUI` (with `EditorGUI`), in place of the fields; `Target` is the script holding its saved values (the live one while playing), and what the Inspector changes on it is saved, one undo step per edit, prefab overrides recorded. `DrawDefaultInspector()` draws the usual fields (ranges as sliders, headers, hidden ones left out). `[CustomInspector("Point Light")]` adds to a built-in component's Inspector, below its fields, changing the object through the C# API. The Sandbox's `SpinnerInspector.cs` puts presets above Spinner's fields and a Raise button under every Point Light. In the Inspector each `EditorGUI` control takes a row like the built-in fields, and `EditorGUI.EntityField` and `EditorGUI.AssetField` are the Inspector's own object and asset pickers, `EditorGUI.EnumField` and `Popup` dropdowns (in Inspectors and windows; the Sandbox's Scene Tools window picks the selected object and a marker prefab with them).
- **Multi-object script editing and Debug mode**: with several objects selected, each script they share (by class, and its place among scripts of that class) shows once; values that differ show as `--`, and edits apply to every one (vectors only in the components changed), live scripts included while playing. The Inspector's **Normal / Debug** toggle (top right; `--inspector-debug` starts in it) shows the object's index and generation, every hidden field read-only (components' and scripts' `[HideInInspector]` ones), and under **Private** a C# script's unsaved fields with their values (the live script's while playing: a patrol's current target, a timer).
- **C# gizmos and context menus**: a script overriding `OnDrawGizmos` draws in the Scene view with `Gizmos.DrawLine`, `DrawRay`, `DrawWireSphere` and `DrawWireCube` (with `Gizmos.Color`, and `Gizmos.Matrix` applied to every shape); `OnDrawGizmosSelected` draws only for selected objects. Outside play mode they run on a script holding its saved values (OnCreate has not run), while playing on the live one; the toolbar's **Gizmos** toggle hides them. Methods with `[ContextMenu("Name")]` are listed in the script's Inspector menu (`...` on its header) and run on the saved values (or the live script), their field changes saved as one undo step. The Sandbox's Patrol draws its route and stops and offers Reverse Points and Add Stop Ahead; WaveSpawner draws its area and the sides its waves use.
- **Edit-mode scripts and Handles**: a script with `[ExecuteInEditMode]` (C++: `ScriptOptions::ExecuteInEditMode`) also runs in the editor outside play mode, on its own instance kept apart from the scene (play mode never sees it): created with OnCreate when it appears, OnUpdate every editor frame, given the saved values again when they are edited, and ended (OnDestroy) when it is removed or disabled, its object goes, play starts or the scripts reload. `Application.IsPlaying` tells the two apart. A custom Inspector's `OnSceneGUI` draws handles in the Scene view while its object is selected (`Handles.PositionHandle` (the move arrows), `FreeMoveHandle` (a dot dragged across the view), `RadiusHandle` (a ring with four dots), `Label` and `DrawLine`, in `Handles.Color`); what they change is saved like the Inspector's edits, one undo step per drag. An Inspector that does not override `OnInspectorGUI` keeps the script's usual fields. The Sandbox's LookAt turns an object toward its target in the editor too; Patrol's stops and the Wave Spawner's area are dragged in the Scene view (RouteInspectors.cs).
- **Scene view draw modes and visibility**: the toolbar's draw mode menu shows the Scene view **Shaded**, as **Wireframe** (every mesh's edges, through other surfaces, on a dark background), **Shaded Wireframe** (the edges over the shaded meshes), **Unlit** (surfaces in their own colors and emission, no lights or shadows) or as **Overdraw** (each mesh a faint additive layer, bright where many overlap); `--draw-mode wireframe|shaded-wireframe|unlit|overdraw` starts in one. **Scene visibility**: the Hierarchy's eye on a row (or **H** for the selection) hides an object in the Scene view, and its pointer makes clicks there pick nothing on it; children follow their parent (dimmed icons). Only the editor's Scene view is affected, in edit and play mode alike; the toolbar's **Visibility** toggle shows and picks everything again without losing the settings, which are kept per scene in `.dimension/SceneVisibility.json`. **Isolation** (**Shift+H**, `--isolate "A,B"`): only the selection and its children show until Shift+H again or the toolbar's **Exit Isolation**.
- **Presets** (like Unity's): a component's "..." menu saves its settings as a `.preset` asset (`Assets/Presets/<Component>.preset`) and applies any preset of its type (to every selected object, one undo step, prefab overrides recorded). A preset's Inspector edits its values (saved at once), applies it to the selection, and makes it the **default for new components** of its type: Add Component (and `[RequireComponent]`) then starts the component with those settings; defaults are kept in the project file. References to objects are left out of presets. The Sandbox has a Warm Lamp Point Light preset.
- **Batch import settings and import defaults per folder** (like Unity's multi-object import editing and folder presets): Ctrl click adds assets to the Project window's selection, Shift click selects a range; several textures (or several models) show their import settings together in the Inspector, values that differ shown as `--`, and a change applies to all of them (each reimported). A texture's or model's Inspector has **Make Default for Folder**: new textures (or models) added to that folder, or a folder in it, start with those import settings (filter, sRGB and mip maps; scale, animations and materials), the deepest folder's default winning; an asset that already has a `.meta` keeps its own. Project Settings > Import Defaults lists them, removes them and applies one to the assets already in its folder. Defaults are kept in the project file.
- **Asset references** (like Unity's Find References In Scene and Select Dependencies): an asset's Inspector lists what it **Uses** and what it is **Used By** (each entry selects that asset). **Find References In Scene** (in its Inspector or the Project window's menu) searches the Hierarchy for `ref:<GUID>`: the objects in the open scene that use the asset, directly or through others (a texture through a material, material slots included), listed in the Hierarchy and the rest dimmed in the Scene view; a prefab instance's objects count by what each uses. The Project window's **Select Dependencies** selects an asset with everything it uses in turn, **Select Used By** the assets using it.
- **Project window list view and Favorites** (like Unity's two-column layout and Favorites): Grid and List buttons switch between thumbnails and a list with **Name, Type, Size and Modified** columns; a header click sorts by that column (again to reverse), folders staying first, and the choice is remembered in the Preferences. Selection works the same in both: Ctrl click adds or removes, **Shift click selects the range** from the last clicked asset. **Favorites** sit at the top of the folder tree: right-click a folder (in the tree or the files) to add it, or Save the current search (`t:Material`, `l:Wall`); a click shows the folder or runs the search, and a favorite can be renamed or removed. They are kept per user in the project's `.dimension/Favorites.json`.
- **Asset previews in the Inspector** (like Unity's preview pane): a model's or prefab's preview is live: drag to turn it, scroll to zoom, double-click to reset. A model with animation clips (or a prefab with animated models) gets a clip menu, Play/Pause (looping) and a time slider, the preview posed at that time. An audio clip shows its **waveform** (a lane per channel), with **Play/Stop**, Loop, the time, and a playhead while it plays; a click on the waveform plays from there. The preview plays straight to the output (not through the mixer) and stops when another asset or object is selected.
- **Scene view camera bookmarks and Frame All**: **Ctrl+Shift+1-9** saves the Scene view's camera (pivot, distance, angles, 2D and its size) as a view, **Ctrl+1-9** goes back to it; the toolbar's **Views** menu lists the nine slots (go, save or replace, clear). Views are kept per scene and per user in the project's `.dimension/SceneBookmarks.json`, so they follow the scene without changing its file. **Frame All** (Shift+F, Edit menu, Views menu) puts everything the scene draws in view (models, sprites and terrains; objects hidden in the Scene view left out). All of these keys can be rebound in Window > Shortcuts.
- **Measuring tool** in the Scene view (toolbar **Measure**, M): click two points to measure between them, snapping to a mesh vertex within a few pixels of the mouse (only the object under it, so hidden vertices behind it are not picked); Shift measures to the surface itself, and off every object a click lands on the ground plane. The ruler shows the straight distance and its X, Y and Z legs (in red, green and blue, each labeled), and the line at the bottom of the view gives all four; before the second click it follows the mouse. A third click starts a new measurement; Esc clears it, then leaves the tool.
- **Selection history and saved selections**: **Alt+Left / Alt+Right** go back and forward through what was selected (objects, or assets in the Project window), like a browser's history; a new selection after going back drops the ones ahead, and selections whose objects were all deleted are skipped. **Ctrl+Alt+1-9** saves the selection (objects with the primary one, or assets) and **Alt+1-9** selects it again; Edit > Selection lists them with Back and Forward. Saved selections are kept per scene and per user in the project's `.dimension/SelectionSets.json`, by object GUID, so they hold across play mode, undo and reopening the scene.
- **Grouping and sorting in the Hierarchy**: **Ctrl+G** (Edit menu, the Hierarchy's object menu) puts the selected objects under a new empty "Group" at the center of their positions, where the first of them was in the Hierarchy and under their common parent (at the root when they have different parents), and selects it to rename; **Ctrl+Shift+G** moves a group's children up to its parent where it was, deleting it when it is an empty object. **Sort Children** (and Sort Children (All Levels)) in an object's menu, and Sort Root Objects in the Hierarchy's own, order objects by name, ignoring case and with numbers in number order (Crate 2 before Crate 10). Objects keep their place in the world through all of it; each is one undo step; objects inside prefab instances are left as the prefab has them.
- **Align With View and Move To View** (GameObject menu, like Unity's): **Align With View** (Ctrl+Shift+F) puts the selected objects at the Scene view camera's position, facing its way (a Camera object then sees what the view sees); **Move To View** (Ctrl+Alt+F) moves the selection together, spacing kept, so its center lands on the point the view orbits; **Align View to Selected** moves the Scene view to the selected object, looking along its forward. Objects are placed in world space whatever their parents (their world scale kept), each move one undo step.
- **Scene view grid settings** (the arrow beside the Grid toggle): the plane the grid lies in (**XZ** ground, **XY** or **YZ** walls; the 2D view keeps XY), its **cell size** (adapting to the view in powers of ten, or a fixed size), its **opacity**, and **Follow selection's height** (the grid moves along its normal to the selected object). Lines through the origin take the color of the axis they run along, every 10th line is brighter, and the grid fades out with distance in its own plane. Kept with the editor preferences.
- **Locked and extra Inspectors** (like Unity's padlock and Add Tab > Inspector): **Lock** at the top of the Inspector keeps it showing what is selected then (objects, several of them, or assets), while the Hierarchy, Scene view and other windows follow the new selection; everything in it still works as usual (edits, multi-object editing, pickers, previews), and its line names what it is locked to. **Window > New Inspector** opens another Inspector, locked to the current selection, each with its own lock and its own model preview; it closes with its window.
- **Inspector folding remembered**: folding a component's header closed folds that component type on every object (a script by its class), kept with the editor preferences, so a long object's Transform or a script you rarely edit stays out of the way everywhere; the component menu's **Collapse All** and **Expand All** fold or open every header on the object at once.
- **Inspector search**: the search box above an object's components shows only those whose names match, or within them only the fields that do; every word must start a word of the component's or field's name ("light int" finds a Point Light's Intensity, "cast" a Mesh Renderer's Cast Shadows, "max sp" a MaxSpeed), scripts match by their class too. Matches show open while searching (folding is kept for afterwards); Esc clears it. Each Inspector window has its own.
- **Profiler timeline**: under the picked frame, its calls as bars along its time (each call of a section where it ran, not just their total), a row per nesting level, with a millisecond ruler and the frame's end marked; scroll to zoom around the mouse, drag to pan, double-click for the whole frame (which it follows from frame to frame until zoomed); hovering a bar gives its name, length and start, and its share of the frame. Up to 4096 calls a frame are kept for it (the totals count every call).
- **Jobs and script calls in the Profiler** (like Unity's): C# jobs show on the timeline under the main thread, a row per worker thread, each job (each batch of a parallel job) as a bar with its name and time (hover for the details), so you can see them overlap the main thread's wait; recordings keep them. **Deep Profile** (beside Timeline, or editor `--deep-profile`) times every C# script callback as a section of its own named after its class (`JobSwarm.OnUpdate`, `Spinner.OnFixedUpdate`, ...), in the frame's sections and on the timeline. C++: `Profiler::Timestamp` / `AddWorkerSpan` (from any thread) and `SetDeepProfiling`.
- **Profiler recordings and frame comparison**: **Save...** writes the frames shown to a `.dprof` file and **Open...** shows one in place of the live frames (its graph, sections, timeline and counters; **Back to Live** returns), to compare runs or share a hitch. **Pin for Comparison** keeps a frame (live or from a recording) and the CPU table then shows it beside the frame picked: each section's milliseconds in both, matched by where it sits in the tree, the change (slower in red, faster in green, small ones grey) and calls when they differ; sections only one frame has show a dash on the other side.
- **Profiling from C#**: `Profiler.BeginSample("Name")` / `Profiler.EndSample()`, or `using (Profiler.Sample("Name")) { ... }`, time a stretch of a script as a section of the Profiler, nested where the script runs (Update > Scripts) and in each other, with its calls, and in the timeline; one left open ends with its frame. `Profiler.SetCounter("Enemies", n)` shows a game value beside the frame's draw calls. The Sandbox's Rainbow script samples its update and sets a Rainbow Hue counter.
- **Debug lines from scripts** (like Unity's `Debug.DrawLine`): C#'s `Debug.DrawLine(from, to, color, duration)` and `Debug.DrawRay(start, direction, color, duration)` (and `DebugDraw::Line` / `Ray` in C++) draw a line in the editor's Scene and Game views while playing, with the gizmos (not in builds); without a duration it lasts until the next update, with one for that much game time. Paused, the last lines stay to look at; stopping play clears them. The Sandbox's C# Spinner draws where it faces, and a fading fan of where it faced.
- **PlayerPrefs and save files** (like Unity's `PlayerPrefs` and `Application.persistentDataPath`): `PlayerPrefs.SetInt` / `SetFloat` / `SetString` and their `Get` (with a default, also when the key holds another type), `HasKey`, `DeleteKey`, `DeleteAll`, written whenever one changes (to a file swapped in whole, so a crash keeps the old one); `SaveFile.Write("slot1", state)` / `Read("slot1", fallback)` / `Exists` / `Delete` keep game state as JSON (fields, lists, dictionaries, vectors). Both live in `Application.PersistentDataPath`: `%APPDATA%\<product name>` in a build, the project's `.dimension\PlayerData` in the editor, so trying the game never touches a build's saves. C++ has `PlayerPrefs::` and `PlayerData::Folder()`. The Sandbox's Greeter remembers the name typed and counts the visits: "Welcome back, Ada! (3 visits)".
- **Input actions** (like Unity's Input Manager): named buttons and axes in **Project Settings > Input**, each with its bindings (keys, mouse buttons, gamepad buttons and axes, each with a scale, -1 for the other way) and a dead zone for gamepad axes; scripts read them by name: `Input.GetButton("Jump")`, `GetButtonDown` (pressed this frame), `GetButtonUp` (released), `Input.GetAxis("Horizontal")` (-1..1, its bindings added up) in C#, `InputActions::` in C++. A project starts with Horizontal and Vertical (WASD, arrows, left stick), Jump (Space, A), Fire (left mouse, right trigger), Submit (Enter, A) and Cancel (Escape, B); **Customize** makes them its own to edit (saved in the project file), Reset to Defaults goes back. Each action's value shows live beside it. The Sandbox's C# VehicleInput drives with Vertical and Horizontal and brakes with Jump.
- **Localization** (like Unity's Localization package): string tables are `.csv` assets (a header row `Key,English (en),French (fr),...`, then a row per key; quoted cells hold commas and line breaks), edited in a spreadsheet and reloaded when saved; the project's tables merge (a key in two tables: the first by path wins, with a warning). `Localization.Get("menu.play")` (and `Get("hud.coins", n)` with `{0}` filled in) in C#, `Localization::Get` in C++; a **UI Text**'s **Localized Key** shows its text in the current language and follows when it changes (a script setting the Text takes over). The language starts as the player's last choice (`Localization.Language = "fr"`, kept in PlayerPrefs), else the system's ("fr-CA" also takes "fr"), else the project's **Default Language** (Project Settings > Localization, also used for texts missing in a language), else the first column. Project Settings > Localization picks the language the editor shows and lists each table's keys translated per language (missing ones in orange); a table's Inspector shows its texts. Builds ship every table. The Sandbox's Demo2D has English, French, German and Spanish menus and a C# LanguageButton cycling them; the Player's `--system-language fr-FR` tries another system language.
- **Data assets** (like Unity's ScriptableObject): a C# class deriving `DataAsset` with public fields is a kind of `.asset` file, made in the Project window (Create > New Data Asset > the class) and edited in its Inspector (saved at once). Script fields of that class (or a base class) pick one of those assets, by drop or from a list of only the fitting ones. While playing, every field referring to an asset holds the same object, made from the file on first use (`OnLoaded()` then runs); saving the asset while playing updates that object in place, and changes scripts make to it last until play stops. The asset's Inspector lists what uses it, and builds ship them. The Sandbox's `BoxPalette` (a `Palette`) colors Demo2D's four boxes through a `PaletteTint` script, each a little later.
- **Hierarchy, tags and active state from scripts** (like Unity's GameObject and Transform): in C#, an `Entity`'s `Parent`, `SetParent(parent, worldPositionStays)`, `Children` / `ChildCount` / `GetChild(i)`, `FindChild("Arm/Hand")`, `Root`, `IsChildOf` and `SiblingIndex`; `SetActive`, `ActiveSelf` and `ActiveInHierarchy`; `Tag`, `CompareTag`, `Entity.FindWithTag` and `FindAllWithTag`; `Layer`; and `GetComponentInChildren<T>` / `GetComponentsInChildren<T>` (inactive objects skipped unless asked) and `GetComponentInParent<T>`. Scripts get **`OnEnable` / `OnDisable`** (after OnCreate for active objects, whenever their object or a parent is switched, and before OnDestroy, also when play stops), and `Behaviour.Enabled` turns one script off and on. C++ scripts have the same (`SetActive`, `CompareTag`, `FindWithTag`, `Parent()`, `SetEnabled`, `OnEnable`). Turning an object's Active box in the Inspector while playing counts too, and a layer changed while playing reaches its 2D and 3D colliders at the next physics step. The Sandbox's Demo2D groups its coins under `Coins`, whose C# `CoinGroup` listens to its children's triggers: the Player picks a coin up (it turns off) and it comes back after 5 s.
- **Cameras, time and the cursor from scripts** (like Unity's Camera, Time, Screen and Cursor): `Camera.Main.ScreenPointToRay(Input.MousePosition)` for `Physics.Raycast(ray, out hit)` (clicking things in the world), `WorldToScreenPoint` (z: distance in front) and `ScreenToWorldPoint`, plus the camera's `FieldOfView`, `OrthographicSize` and `Orthographic`; screen points are pixels of the view the game is shown in (`Screen.Width` / `Height`: the Game view in the editor, the window in a build), top-left origin, and `Input.MousePosition` is in the same view while playing (`Input.MouseDelta` and `GetMouseButtonDown` are new too). **`Time.TimeScale`** (0-100) slows or freezes the game: script steps, `time`, physics, animation, particles and `WaitForSeconds` follow it, UI animation keeps real time, and `UnscaledDeltaTime` / `UnscaledTime` give the real clock. **`Cursor.LockState`** (`Locked`: hidden and held for mouse look) and **`Cursor.Visible`** apply while the game has input; in the editor Escape gives the cursor back until the Game view is clicked (the editor's windows ignore a locked mouse), and play stop restores it. C++ has `CameraProjection::`, `Scene::SetTimeScale` and `Input::SetCursorMode`. The Sandbox's Navigation scene sends the ogre where you click (C# `ClickToMove` moves its flag) and T toggles slow motion.
- **2D physics queries from scripts** (like Unity's Physics2D): `Physics2D.Raycast(origin, direction, out hit)` (the nearest collider: `Entity`, `Point`, `Normal`, `Distance`), `RaycastAll` (every object along the ray, nearest first), `OverlapCircle`, `OverlapBox(center, size, angle)`, and `OverlapPoint` / `OverlapPointAll` (the collider containing a point, e.g. `Camera.Main.ScreenToWorldPoint(mouse)`), all with layer masks; `Rigidbody2D.AngularVelocity` (degrees per second) and `AddTorque` join `Velocity`, `AddForce` and `AddImpulse`. C++ has `Physics2DWorld::RaycastAll`, `OverlapPoint`, `GetAngularVelocity` / `SetAngularVelocity` and `ApplyTorque`. Clicking a box in the Sandbox's Demo2D kicks it up, spinning away from the side clicked (C# `ClickToKick` on the camera).
- **3D shape casts and spin from scripts** (like Unity's Physics and Rigidbody): `Physics.SphereCast` and `BoxCast` (a sphere or turned box swept along a direction: the first collider it touches, where, its surface normal and how far the shape moved; a collider it starts inside is hit at 0), `Physics.RaycastAll` (every object along a ray, nearest first) and `OverlapBox`, all with layer masks and `Ray` overloads; `Rigidbody.AngularVelocity` (radians per second), `AddTorque`, `AddForceAtPosition` and `AddImpulseAtPosition` (off the center of mass they turn the body too). C++ has `Physics3DWorld::SphereCast`, `BoxCast`, `Get/SetAngularVelocity`, `AddTorque` and `Add{Force,Impulse}AtPosition`. In the Sandbox's Navigation scene, right-clicking a crate shoves it where the click lands (C# `Shover`).
- **Collision details** (like Unity's Collision): `OnCollisionEnter(Collision)`, **`OnCollisionStay`** (every physics step while touching) and `OnCollisionExit(Collision)` give the other object, the contact points (point, normal toward this object, separation), the contacts' `Normal`, the `RelativeVelocity` (this object's minus the other's as they met) and the hit's `Impulse` (closing speed times the pair's reduced mass), in 2D and 3D, C# and C++. The `Entity` overloads still work (the new ones call them by default), and Stay is only sent to C# classes that have one and, as in Unity, not while both bodies sleep. A resting 3D body falling asleep no longer gives a spurious Exit (and a new Enter when it wakes): only coming apart does. The Sandbox's Navigation crates flash when they hit something hard (C# `HitFlash`, e.g. shoved into a wall).
- **Mouse events on objects** (like Unity's OnMouse* messages): scripts on an object with a 3D or 2D collider get `OnMouseEnter`, `OnMouseOver` (every frame) and `OnMouseExit` as the pointer moves over it (picked through the primary camera, the nearest collider; not through UI, and nothing for inactive objects), `OnMouseDown` when pressed on it, then `OnMouseDrag` every frame while held (even off it) and `OnMouseUp` on release, plus `OnMouseUpAsButton` when released over it (a click). They follow the pointer the UI uses: the Game view in the editor, the window in a build. **`OnTriggerStay`** comes every physics step inside a trigger (2D and 3D; none while both bodies sleep). C# only calls Stay and the mouse callbacks on classes that have them. `Rigidbody` gains `IsDynamic`, `IsSleeping` and `WakeUp()`, and setting a 3D body's velocity now wakes it. C++ has the same callbacks and `Scene::GetObjectUnderPointer` / `PickObject`. In the Sandbox's Navigation scene the crates can be dragged around (C# `Draggable`).
- **Scripts finding each other** (like Unity's GetComponent and FindObjectOfType): in C#, `GetComponent<T>()`, `GetComponents<T>()`, `GetComponentInChildren` / `InParent`, `HasComponent<T>` and `AddComponent<T>()` take a script class as well as an engine component (a script added while playing starts at once: OnCreate, OnEnable; a physics component gets its body at once, and a `Rigidbody` added to an object with only a collider makes it dynamic; C++ `Scene::AddComponentByName`), and `FindObjectOfType<T>()` / `FindObjectsOfType<T>()` find scripts or components in the scene (active objects unless asked). A public field of a script type (`public Scoreboard Board;`, also lists) is picked in the Inspector as an object that has such a script (`Hits (Scoreboard)`; derived classes count) and holds that object's script while playing: every new script's object is made before any field is set, so they may refer to each other. C++ has `Scene::AddScript`. The Sandbox's Navigation crates report hard hits to a `Scoreboard` text through their HitFlash's `Board` field.
- **Cloning and removing from scripts** (like Unity's Instantiate and Destroy): `Instantiate(entity)` copies an object with its children, components and scripts, at the original's place or a given world position and rotation, as a root object or under a parent; while playing the copy's scripts start with the original's current field values, its bodies and sounds start at once, and references inside the copied objects point to the copies (`Instantiate(script)` returns the copy's script). Prefabs take a rotation and parent too (`prefab.Instantiate(position, rotation, parent)`). `Destroy(component)` and `Destroy(script)` (`Destroy(this)`) take one off its object at the end of the frame (a script gets OnDisable and OnDestroy; a physics component's body is made again without it; Transform and the like stay). C++ has `Scene::Instantiate`, `InstantiatePrefab(..., rotation, parent)`, `RemoveScriptDeferred` and `RemoveComponentDeferred`. Pressing C in the Sandbox's Navigation scene drops copies of a crate (C# `Cloner`, at most 8).
- **The Animator from scripts, read back** (like Unity's Animator): `GetFloat`, `GetInteger` and `GetBool` (what was set, else the controller's default; a trigger is true until it fires), `HasParameter` and `ResetTrigger`; the current state per layer (`GetCurrentState(layer)`), its progress (`NormalizedTime`: 0.5 halfway, 2.3 in its third loop), `IsInTransition`, `TransitionProgress` and `PreviousState` (the state fading out); `Speed`; and the layers (`LayerCount`, `GetLayerName`, `GetLayerIndex`, `GetLayerWeight` / `SetLayerWeight`). The Sandbox's TentacleBrain pokes its tentacle only once the current state has played through and no crossfade is running, and logs each transition with the state it came from.

- **Motion blur and lens dirt** (Scene Settings > Post Processing > Lens Effects): **Motion Blur** smears the image along how each pixel moved on screen since the last frame, its **Shutter** the fraction blurred, capped so fast turns stay readable. It reads a **velocity buffer**: the camera's motion for every pixel (reprojected through the depth buffer with the last frame's view), then each object that moved or changed pose since the last frame drawn over it with its last world matrix (and, skinned, its last pose), so a spinning fan, a passing car or a waving arm blurs along its own motion while the still world around it stays sharp. Simulated vertices (cloth, soft bodies, ropes, water surfaces, dents) use where each vertex was last frame, sprites, text and tilemaps their object's last transform, and particles (CPU and GPU) their own velocity, so fast sparks streak along their flight. The ocean's waves give their own motion too (each ring vertex where the waves had it at the last frame's time, although the rings follow the camera), and water surfaces, which are see-through and not in the depth buffer, write theirs wherever they are in front, so TAA follows the swell instead of smearing it. Physics moves things in fixed steps: a fast body blurs steadily with its Rigidbody's Interpolate on (cloth and soft bodies likewise with their own **Interpolation** set to Interpolate: their shapes are drawn between the last two steps', so they blur on every frame, not only on the frames where they stepped). A reconstruction filter (after McGuire et al.) samples along the longest motion in the tiles around each pixel, so fast objects smear out over the background behind them, not only within their outline. Each Mesh Renderer's **Motion Vectors** (as Unity's) chooses Per Object Motion (the default), Camera Motion Only, or Force No Motion (sharp however the camera turns, e.g. a weapon held in view); C#: `MeshRenderer.MotionVectors` (`MotionVectorGenerationMode`). TAA reprojects through the same buffer, so moving objects keep their history instead of being clipped back to a jagged frame. A camera cut starts the motion over; **Lens Dirt** is a texture of smudges lit by the bloom (**Dirt Intensity**). Both in the Game view and Player. C++: `SceneSettings::MotionBlur` / `MotionBlurIntensity` / `LensDirt` / `LensDirtIntensity`, `MotionBlur.frag`, `Velocity.vert`, `SceneRenderTarget::GetVelocity` / `GetVelocityTiles`, `MeshRendererComponent::MotionVectors`. **Rendering (Vulkan 1.3)**
- Dynamic rendering, synchronization2 and a bindless texture table. There are no render-pass objects and no per-material descriptor sets.
- volk loads Vulkan directly from the GPU driver, so **no Vulkan SDK is required** to build or run.
- VMA for memory, frames in flight, deferred GPU resource destruction, and a per-frame transient ring buffer.
- HDR linear pipeline with an sRGB/ACES composite and physically based shading (Cook-Torrance GGX) for 1 directional light and up to 1,024 point and spot lights, with sky reflections.
- **Clustered lighting**: the view is split into 16 x 9 tiles x 24 depth slices (logarithmic; linear for orthographic cameras), and each frame a **compute shader** lists, per cluster, the point and spot lights whose range reaches it (one invocation per cluster, testing each light's sphere against the cluster's view-space bounds). A pixel shades only its cluster's lights, so many small lights cost little: `Scenes/Lights.scene` (256 bobbing point lights over a field of pillars) renders in 3.2 ms with GPU culling, 4.0 ms with the clusters built on the CPU and 18.3 ms when every pixel shades every light (Debug build). The Stats panel shows the light count and switches GPU culling; the Player's `--cpu-light-culling` and `--no-clusters` are there for comparisons (all three images match exactly).
- Post processing in Scene Settings: physically based bloom (thresholded 13-tap downsample and tent upsample over a mip chain), exposure, ACES tonemapping, vignette and FXAA. Bloom and FXAA also show in the Scene view.
- **MSAA** (Scene Settings: Off, 2x, 4x, 8x, clamped to what the GPU supports): the main pass draws into multisampled color, entity-ID and depth images that resolve at the end of the pass (color averaged, IDs and depth from sample 0), so picking, SSAO and depth of field keep working. It combines with FXAA. Demo3D uses 4x.
- **Screen-space reflections** (Scene Settings, perspective cameras): opaque surfaces also write their normal, roughness and reflection weight to a surface buffer; a full-screen pass marches each reflected ray through the depth buffer (steps growing with distance, jittered, refined by bisection; rays that meet the surface they left, or the back of something, keep going) and, where it hits something on screen, replaces the probe or sky reflection with what is there. Hits fade out at the screen edges, toward the end of the ray, for rays heading back at the camera and up to Max Roughness; a small blur hides the jitter. Intensity, Max Distance, Thickness, Max Roughness and Steps are adjustable. `Scenes/Particles.scene` has a glossy floor reflecting glowing pedestals.
- **Temporal anti-aliasing** (Scene Settings, game views): each frame is rendered with a different sub-pixel offset (a Halton sequence) and blended with the previous frames, reprojected through the depth buffer, with the history clipped to the current neighborhood's colors so moving objects do not smear. Edges, thin lines and shimmering detail come out smooth; New Frame Weight trades smoothness for responsiveness. The Scene view is never jittered.
- **Volumetric fog** (Scene Settings, perspective cameras): height fog that each view ray marches through to the visible surface, lit by its own Fog Color and by the sun wherever the shadow map lets the sun reach (light shafts, brighter looking toward the sun by Anisotropy). Density, base height, height falloff, max distance and steps are adjustable; with TAA the per-frame jitter of the march averages out.
- **Decals**: a **Decal** component projects a texture (or a soft round spot) along the object's -Z onto whatever lies in its box: Multiply darkens (dirt, scorch marks), Alpha paints over and Additive glows. Surfaces turned away from the projector fade out.
- **Terrain** (GameObject > 3D Object > Terrain): a height field from a grayscale heightmap (16-bit keeps detail) or fractal noise (seed, scale, octaves, roughness, an optional flat center for play areas), with a list of up to 16 surface **Layers** (each a name, a color, an optional texture and its tiling in world space; add, remove and reorder them in the Inspector), the first three laid out by slope and height (grass on gentle ground, rock on steep slopes, snow up high). It renders as one mesh with shadows and collides as a Jolt height field that matches the surface exactly. `Scenes/Terrain.scene` has boulders rolling into a crater under fog and TAA. **Sculpting and painting**: with a terrain selected, the Inspector's tools Raise, Lower (or Shift with Raise), Smooth and Flatten the height under a round brush dragged in the Scene view, and **Paint** brushes any chosen layer over the automatic blend; Brush Size and Strength are adjustable, each stroke is one undo step, the edits are saved with the scene (16-bit heights) on top of the heightmap or noise, the collider follows, and Clear Sculpting and Painting returns to the generated terrain.
- **Terrain details**: the Inspector's **Trees**, **Grass Tufts** and **Erase Details** brushes paint where trees (or bushes and rocks) and grass grow. Each kind is a mesh (Tree Mesh, Grass Mesh, with an optional material) scattered over a jittered grid at Density per 100 m2 where painted at full strength, turned at random and sized between Min and Max Scale, only on ground flatter than Max Slope; the same paint gives the same placement every time. The instances batch into instanced draws with shadows, picking one selects the terrain, and with a **Tree Collider Radius** trees collide as trunk capsules as tall as their mesh. **Clear Details** removes them.
- **Craters**: `Terrain::DigCrater(scene, point, radius, depth)` (C#: `TerrainTools.DigCrater`) blows a crater into whatever terrain is under a point, at any time: a bowl Radius across and Depth deep with a rim of thrown-up earth, painted dirt and cleared of trees and grass; while playing the terrain redraws and its collider is rebuilt, so things roll into it.
- **Terrain holes and painted layers**: **Dig Hole** (Shift: **Fill Hole**) cuts holes for caves, tunnels and wells: every triangle touching a hole sample leaves both the mesh and the Jolt height field, so things fall through, rays pass and no trees or grass grow there; holes are saved as one bit per sample. Layers past the first three are painted only (a new terrain also has **Dirt**, **Sand** and **Moss**); weights live in RGBA splat maps, four layers each, and the shader loops over the terrain's layers. Only the layers painted are saved (a byte per layer per sample); scenes saved with the older six fixed layers load into the list as they were.
- **Terrain normal maps and height blending**: each terrain layer can have a **Normal Map** (tiled with its texture, bent by **Normal Strength**), blended by the layers' weights onto the surface. With **Height Blend** (0-1) a layer's texture brightness is its height, and where layers meet the higher parts win: stones show through grass in clumps with crisp edges instead of fading evenly. A layer can be **Triplanar**: projected from the sides as well as from above, blended by which way the ground faces (its normal map too, by Golus's UDN blend), so stones keep their shape down cliffs instead of stretching into streaks. `Scenes/Terrain.scene` uses generated grass and stone textures and a stone normal map, the stone triplanar.
- **Terrain layer rules**: a layer with **Rule** lays itself out where the ground's height (0-1 of the terrain's Height) and slope (degrees) fall in its **Height Range** and **Slope Range**, fading out over **Height Fade** and **Slope Fade** past them and broken into patches by **Noise** (about **Noise Scale** meters across). Later layers cover earlier ones and the first is the ground under all, so any number of layers place themselves (sand low and flat, rock on slopes, snow up high, moss in patches); terrains without rules keep the older automatic first three. Painting still overrides. Each layer's **Trees** and **Grass** (0-1) make the terrain's tree and grass details grow on it by themselves, as thickly as the layer covers the ground (painting adds more). `Scenes/Terrain.scene` lays out rock, snow and patchy moss by rules, with bushes growing in the moss.
- **Terrain stamps**: the **Stamp** brush lays a grayscale image (a mountain, a crater, a mesa) over a square of twice the brush size, turned by **Stamp Rotation**: the ground rises toward the stroke's starting height plus the image times **Stamp Height**, or with Shift sinks by it. It only ever moves one way, so stamps overlap without flattening each other.
- **Erosion**: the **Erode** brush rains on the ground under it: each drop runs downhill, picking up sediment where it speeds up on steep ground and dropping it where it slows or climbs, so slopes grow gullies and valleys fill with the washed-down material (which only moves: the terrain keeps its volume). Holding it longer weathers more.
- **Terrain paths** (roads and rivers): a **Terrain Path** is a smooth curve through its Points (drawn in the Scene view with its width). **Apply to Terrain** (Inspector, one undo step) bakes it into the terrain: a **Road** levels the ground across Width to the curve's height and blends into the land over Falloff; a **River** carves a rounded channel Depth below the curve and lowers its banks to it. Either paints a layer along it (dirt roads, sandy river beds).
- **Grass in the wind**: terrain grass tufts sway in the scene's **Wind** (Scene Settings: a direction and speed, plus **Wind Gusts**, waves of stronger wind moving across the field, with a flutter), bending more toward their tips and keeping their length, and they part around characters and dynamic rigid bodies standing or rolling through them (the 16 nearest the camera). Both happen in the vertex shader, so shadows bend too; a terrain's **Grass Sway** and **Grass Bending** scale them (0 = rigid).
- **Fur**: a **Fur** component draws the object's mesh again as Shells layers pushed out along its normals by up to Length, keeping only the strands' cross-sections (Density per UV unit, Thickness at the root, tapering, of random heights), so spheres turn fluffy and boxes become carpet. The strands droop under gravity, sway in the scene's Wind, darken toward the roots (Root Shade) and take Tip Color at the tips; the shells cast and occlude only their strands, batch into instanced draws and follow skinned meshes.
- **Screen-space global illumination** (Scene Settings): a few cosine-weighted rays per pixel march through the depth buffer, and where they meet a surface on screen its lit color bounces onto the pixel (times its diffuse color), so a red wall tints the floor and ceiling beside it. It adds to the ambient, sky and probe light; Intensity, Distance, Thickness and Rays are adjustable, and the rays turn every frame. The trace runs at half resolution and a temporal filter blends it with the last frame's result (reprojected through the depth buffer and clamped to the new trace, so moving light does not smear), which keeps it smooth even without TAA.
- **Volumetric clouds** (Scene Settings): a layer of clouds between **Base** and **Top** altitudes, made of fractal noise thinned by **Coverage**, flat-bottomed and rounded on top, drifting with the scene's Wind. The sky shader marches each view ray through the layer: every step is lit by the sun through the cloud between it and the sun (bright silver edges toward the sun, dark undersides) and by the sky from above, and far clouds fade into the haze. Works over the gradient sky and HDR sky textures; Density, Scale and Steps are adjustable.
- **Cloud shadows**: with clouds on, the sun reaching each surface passes through the cloud layer along its rays (a few samples of the same noise), so cloud shadows drift over the land with the wind.
- **Path placement** (like Unity's Spline Instantiate): a **Path Placer** lays copies of a prefab (or of a **Source** object in the scene) along a smooth curve through its Points, open or **Closed**: one every **Spacing** meters along it after **Start Offset**, **Side Offset** to its right, facing along it (**Align To Path**) and turned by **Rotation**, scattered by **Random Rotation** and **Random Scale** from a **Seed**, and dropped onto the terrain under each (**Snap To Ground**), for fences, rows of trees and lamp posts. The selected placer draws its curve and a tick where each copy goes; **Place Along Path** (Inspector, one undo step) makes the copies its children, replacing the last ones, and **Clear** removes them.
- **Weather**: a **Weather** component makes rain and snow fall around the primary camera (GPU particles over Area, starting Height above it, slanted by the Wind, stopped by what the camera sees; rain as streaks, snow drifting), and marks every surface: **Wetness** darkens them and makes them glossy (flat ground most, so it mirrors the sky), **Snow Cover** settles snow on what faces up, patchy at its edge. Very wet flat ground collects **puddles** in patches (more the wetter it gets): dark, mirror-smooth (reflecting the scene through screen-space reflections) and, while it rains, spattered with spreading ripple rings. **Lightning** (0 = none, 1 = every few seconds) strikes at random: a double flicker that lights the clouds and the whole scene, then the **Thunder** clip through the object's Audio Source a moment later, as if from the strike's distance. Scripts fade them in and out (C#: `Weather.Rain`, `Snowfall`, `Wetness`, `SnowCover`).
- **Reflection probes** (GameObject > Light > Reflection Probe): capture the surroundings at a point (six HDR renders from its position, converted to an equirectangular image whose mips are **GGX-prefiltered**, one roughness per mip, with filtered importance sampling). Surfaces inside a probe's box reflect it instead of the sky, blended per pixel: smaller boxes take priority, and each probe fades out over its **Blend Distance** inside its walls into overlapping probes or the sky; with Box Projection, reflections line up with the box's walls. Probes re-capture when first shown, when moved, resized or given another resolution, when play starts, on **Bake Reflection Probes** (Inspector), or every frame with Realtime. Up to 8 per view; the selected probe draws its box. Demo3D has one covering the arena, so the chrome sphere, gold torus and metal tentacles reflect the scene.
- **Light probe volumes** (baked global illumination): a **Light Probe Volume** fills its box with a grid of probes (Probes X/Y/Z). Baking renders the scene around each probe (one probe per frame, so the editor stays responsive) and stores its incoming light as 9 spherical-harmonic coefficients, saved with the scene. Surfaces inside the box take their ambient light from the trilinearly blended probes instead of the sky, so light bouncing off a red wall tints what stands next to it; the effect fades out over Blend Distance at the walls and scales by Intensity. Volumes bake when first shown or on **Bake Light Probes** (Inspector, with progress), and up to 4 apply per view; the selected volume draws its box and probes. With **Realtime**, a volume keeps capturing its probes again, **Probes Per Frame** at a time in turn, so bounce light follows lights and objects that move (a red glow from a lamp by a red wall turns green when the lamp moves to the green one), and since each capture sees the volume's own light from the last pass, light bounces more than once.
- **Order-independent transparency** (Scene Settings, game views): transparent meshes are drawn in their own pass into a weighted color sum and a transmittance product (weighted blended OIT, weighted by alpha and distance), then resolved over the scene, so intersecting and nested see-through objects blend correctly from every angle instead of one object covering another by sort order.
- **Refraction**: a Transparent material's **Refraction** bends what is seen through it by its normals (water, glass, ice), more up close, tinted by its color; the frame then draws its transparent meshes in their own pass (as with OIT) so they can read the finished opaque image (game views).
- **Depth of field** (Scene Settings > Post Processing): objects nearer or farther than Focus Distance blur, reaching the full Bokeh Size (a fraction of the image height) Focus Range away. A half-resolution prefilter computes each pixel's circle of confusion from the depth buffer. A 32-sample disc gather then blurs it, limiting background samples so sharp foreground edges do not bleed, while blurred foreground still spreads over what is behind it. Composite blends the result in before tonemapping. It applies in the Game view and Player (the Scene view stays sharp); `Scenes/Instancing.scene` uses it for a tilt-shift look.
- **Occlusion culling** (Scene Settings, on by default): after the opaque pass a compute shader reduces the depth buffer to a grid of cells (about 192 across), each holding the farthest depth drawn in it, into memory the CPU reads once that frame is done. A frame or two later every mesh whose box lies behind what was drawn in all the cells it covers (and one cell around) is skipped in the depth, main and transparent passes; it still casts its shadow. While the camera moves (up to 5 m and 60 degrees from where the grid was drawn) the grid is first **reprojected** into the current view: each cell becomes a quad at its farthest depth, put where the camera now sees it, and each new cell keeps the farthest quad over it; cells no quad reaches (just come into view, or uncovered by the move) hide nothing, so what the move reveals is drawn at once. C++: `OccluderDepth::Reprojected`. A wall in front of 200 cubes draws 5 meshes instead of 209, and the image is the same pixel for pixel as with `--no-occlusion` (Player), also when some cubes show over the wall; a camera sliding past a wall at 20 m/s in front of the Instancing scene's 1,440 cubes keeps 1,411 of them culled, again pixel for pixel the same (Player `--fixed-dt 0.0166` makes such runs repeatable). The Stats panel counts the meshes occluded.
- **GPU instancing**: meshes that share a mesh, sub-mesh, material and pipeline are drawn with one instanced call per pass (main, depth prepass and every shadow map), with per-instance transforms and entity ids (for picking) in a GPU buffer. **Skinned meshes** instance too (each instance carries the address of its own skinning matrices, so every copy keeps its pose), and **transparent meshes** merge runs of neighbours in their back-to-front order (instances blend in order, so the result is identical). Materials are uploaded once per distinct content, so objects using the same simple Mesh Renderer settings batch too. In `Scenes/Instancing.scene` (1,600 cubes) this takes the frame from 4,903 draw calls to 37.
- **One render list per frame**: Mesh Renderers are resolved once per frame (mesh, world-space bounds, uploaded materials and skinning matrices, and a batch id for each part). Each pass (shadow cascades, point and spot shadow faces, depth prepass, main) then only culls against precomputed world bounds and buckets visible parts by batch with a counting sort, writing all instance data into one buffer. On a 10,000-cube scene, CPU recording fell from about 9 ms to 2.6 ms per frame (1.7 ms of it building the list), and the frame from 10.3 ms to the display's pacing limit (3.5 ms). Window > Stats shows instanced meshes and has a toggle to compare; the player logs CPU update, recording and list times on exit.
- **LOD Groups** (like Unity's): a **LOD Group**'s children are levels of detail of one object, child 0 the most detailed. Each frame it shows the one child that fits how tall the object looks on screen (its **Size**, or its children's mesh bounds, over the distance, as a fraction of the view's height, times **Bias**): LOD 0 above **LOD 1 Below**, then LOD 1, LOD 2 and LOD 3 down to their thresholds, and nothing below **Cull Below**. The choice is made once per frame for the camera, so shadows draw the same level. Within **Fade Width** above a threshold the two levels **cross-fade**: they share the pixels in a 4x4 dither (in shadows and the depth prepass too), so a switch is not a pop. The Inspector shows Unity's **LOD bar** (a colored segment per level and Culled, on a square-root scale; drag a divider to move that threshold) and lists which child is which level; the selected group shows the size it measures.
- **Generated LOD levels**: with **Generated Levels** (1-3), a LOD Group's own Mesh Renderer is LOD 0 and the simpler levels are made from its mesh, each keeping **Reduction** of the triangles of the one before. The simplifier collapses edges cheapest first by quadric error (open borders, borders between materials and UV seams cost more to move, no triangle may turn over, and it stops where the shape would move more than a few percent of its size). It moves corners onto neighbouring ones, so vertices, UVs, tangents and skinning stay as they were. Levels are made the first time they are seen and kept until the mesh is reloaded. `Scenes/Navigation.scene` has a row of statues going from a detailed version to a sphere to a block with distance.
- **Impostors**: with **Impostor**, a LOD Group gets one more level after its meshes, down to Cull Below: a flat picture of LOD 0, turned to face the camera, showing whichever of 8 sides is nearest the camera's, from the nearer of two heights (a little from above, or steeply from above, so a statue looked down on from a hill or a tower is not flattened). The pictures are rendered once into three mip-mapped atlases (LOD 0 alone: its surface colors with alpha where it covers, its normals in each side's view, and its roughness and metallic with each texel's **depth**) and drawn cut out and **lit live** like any surface, the normals as its normal map (each side's view is the quad's own frame), so a sun that turns, a day-night cycle or a passing point light shades impostors as it shades their meshes, metal shine included; they cross-fade with the last mesh level like the others and are rendered again only when LOD 0 changes, one group a frame. LOD Groups with the same contents (a row of the same statue, each turned its own way) share one set of atlases. Each pixel is drawn at the depth its texel had on the mesh, so an impostor meets the ground and whatever stands in it as its mesh does (a half-buried boulder is cut along its curve, a pole through a statue passes in front of and behind the right parts), and SSAO and fog see its real shape. They **cast shadows** too: a second cutout of the side nearest the sun, turned to it, drawn only into the shadow maps and at its own depth along the light, so a far statue's shadow falls as its mesh's would and it shades itself without acne (`MeshImpostor.frag`, `DepthImpostor.frag`, `ShadowImpostor.frag`). Far away a row of statues looks the same as its full models; the farthest statue in `Scenes/Navigation.scene` is one.
- **Screen-space ambient occlusion** (Scene Settings > Post Processing > Ambient Occlusion): a depth prepass of opaque geometry, 16-sample hemisphere SSAO at half resolution with normals reconstructed from depth, and a depth-aware blur. The main pass reuses the prepass depth, and the occlusion darkens only ambient light and sky reflections, not direct light. Radius, Intensity and Bias are adjustable, and Show Occlusion displays the AO buffer. Perspective cameras only; Demo3D has it on.
- **Material assets** (`.mat`): base color, normal, metallic-roughness and emission maps, tiling/offset, Opaque/Cutout/Transparent blend modes, double-sided rendering. Normal mapping uses a model's authored vertex tangents (glTF TANGENT, with handedness); models and built-in primitives without them get **generated tangents** from their UV layout (angle-weighted per corner, as MikkTSpace does, with vertices split where mirrored UVs meet), and triangles without UV area fall back to a frame from screen-space derivatives. Per-draw material data reaches shaders through buffer device addresses.
- **Asset previews**: materials (on a lit sphere), models (with their own materials) and prefabs (as built) show rendered, framed from a little above against the sky, in the Project window's thumbnails and at the top of the Inspector (like Unity's). Each is rendered by the editor's own small preview scene into a picture kept per asset, a couple a frame, and again when a material's values change or one of its textures has loaded, or a model or prefab's file changes.
- **Asset labels and search**: any asset can carry labels (the Inspector: add one, pick a used one, or remove one), kept in its `.meta` file. The Project window's search runs across the project: words match file names, `t:Type` an asset type (Texture, Mesh, Material, Prefab, Scene, Audio, Font, AnimatorController, Timeline, SpriteAtlas; a prefix will do) and `l:Label` a label, all together (`l:props t:mat`).
- Cascaded shadow maps for the directional light: up to 4 cascades in a 2x2 atlas, split over the shadow distance with practical (log/uniform) splits, each fitted and texel-snapped to its slice of the camera frustum. Cascades blend at their borders, shadows fade out at the shadow distance, and Debug Cascades tints each cascade. 3x3 PCF and normal-offset bias.
- **Soft shadows (PCSS)**: with Soft Shadows on the Directional Light, a blocker search finds the average occluder depth and the penumbra widens with the distance between occluder and receiver, set by Light Angle (the light's apparent diameter; the sun is about 0.5 degrees). Contact points stay sharp while long shadows blur. Distances are measured in world units per cascade, and a rotated Vogel-disk kernel (24 taps, seeded in light space so it does not swim) keeps the cost bounded. Demo3D uses it.
- Spot lights (GameObject > Light > Spot Light): range, outer and inner cone angles with a smooth falloff, a cone gizmo, and optional shadows from a single perspective shadow map.
- **Light cookies**: a Spot Light's Cookie texture is projected through its cone like a gobo, and its color multiplies the light (stained glass, window panes, flashlight rings). The outer cone maps onto the texture's inscribed circle, and the cookie turns with the light's roll. The sample `Sprites/WindowCookie.png` casts a four-pane window. A **Point Light's Cookie** is an equirectangular (2:1) image wrapped around the light in its local space (the image center faces its forward axis), so it turns with the light; Demo3D's Lantern casts the pierced-tin pattern `Sprites/LanternCookie.png`.
- Point- and spot-light shadows: up to 4 point or spot lights with Cast Shadows share a shadow atlas (512 px per tile): point lights render 6 cube faces, spot lights one tile. The shader picks the face from the direction to the light and compares linear distances (bias in world units) with 3x3 PCF.
- Sky: a procedural gradient with a sun disk, or an equirectangular **HDR sky texture** (`.hdr`, loaded as RGBA16F with mips) with intensity and rotation (Scene Settings > Sky).
- **Image-based lighting** from the HDR sky: reflections come from a **GGX-prefiltered** copy of the sky (up to 1024 x 512, one roughness per mip, filtered importance sampling, rebuilt when the sky changes), diffuse ambient comes from 9-coefficient spherical harmonics computed when the image loads, scaled by Ambient Intensity and Reflection Intensity. Demo3D uses a generated clear-sky HDR whose sun matches the directional light. Per-camera clear flags.
- Frustum culling for meshes and their shadow casters.
- Batched sprites with sorting order, sprite sheets and flipping, plus world-space **Text (3D)**.
- **Sprite Atlases** (`.spriteatlas`, Project > Create > New Sprite Atlas, starting with the folder's textures): sprites packed into one page (shelves, tallest first, Padding apart with each sprite's edge repeated into it, on the smallest power-of-two page up to Max Size; what does not fit is listed as not packed). Sprite Renderers showing a packed texture draw from the atlas, their UVs (sprite sheet frames and flips included) moved into its region, unless they tile. The Inspector edits the list, padding and size and shows the page; builds ship an atlas whenever one of its sprites ships. `Sprites/Sprites.spriteatlas` packs the 2D demo's sprites.
- **Sprite Editor** (Window > Sprite Editor, or Sprite Editor... on a texture, like Unity's): slices the selected texture into named sprites by a grid (a number of cells, or cells of a size with an offset and gaps; empty cells left out) or automatically (each group of touching pixels above an alpha, as its box, row by row); each sprite's name and rectangle can be edited, sprites added and removed, and Apply saves them with the texture's import settings. A Sprite Renderer then picks one from a **Sprite** list and draws just that part, sized to it (atlases still apply). The 2D demo's tiles are sliced into Grass, Dirt, Stone, Planks, Ice, Metal, Bush and Crate, and two bushes use one.
- **Tilemaps** (GameObject > 2D Object > Tilemap): a sprite-sheet tileset painted into a sparse grid, drawn through the sprite batcher, with an optional static Box2D collider built from merged row boxes. **Window > Tile Palette** picks a tile; with a tilemap selected, left-drag in the Scene view paints and Shift-drag (or the Erase tool) erases, one undo step per stroke. Demo2D's level is one tilemap (generated `Sprites/Tiles.png`).
- **Skeletal animation**: glTF skins (joints, weights, inverse bind matrices) and animation clips (linear, step and cubic-spline keys, the splines with their tangents). Linear-blend skinning runs on the GPU in the mesh shader, with shadows. The **Animator** component handles clip playback, speed, looping and `CrossFade(clip, seconds)`.
- **Blend shapes** (glTF morph targets, like Unity's blend shapes on a Skinned Mesh Renderer): a model's morph targets import by name (the mesh's target names, matched across its parts) with the file's default weights, scaled with the model and kept through tangent generation and the import cache. The Mesh Renderer's Inspector shows a **Blend Shapes** section with a 0..100 weight slider per shape (one undo step per drag, **Reset Weights** for the model's own); weights are saved with the scene. Each frame the weighted shapes move the model's vertices and normals into the frame's vertex stream (the path cloth uses), with GPU skinning still applied on top, so faces can smile while the body walks: for skinned models in a compute shader (`BlendShapes.comp`, one invocation per vertex over the active shapes' deltas, uploaded once per model; bounds grow by how far the weighted shapes reach), pixel-identical to the CPU path (`--cpu-blend-shapes` in the Player compares); unskinned models stay on the CPU, so their moved vertices also give their per-object motion vectors. glTF weight animations become clip channels the **Animator** plays (blended through crossfades, blend trees and Override / Additive layers; a shape the playing clip does not animate keeps the renderer's weight). C#: `MeshRenderer.BlendShapeCount`, `GetBlendShapeName` / `GetBlendShapeIndex`, `GetBlendShapeWeight` / `SetBlendShapeWeight`. C++: `MeshData::BlendShapes` / `ApplyBlendShapes` / `FindBlendShape`, `MeshRendererComponent::BlendShapeWeights`, `AnimationClip::WeightChannels`, `Pose::Weights`.
- **Animator Controllers** (`.controller`) are state machines like Unity's. They have float, int, bool and trigger parameters, and states with a clip, speed and loop flag. Transitions run from a state or from Any State, with conditions, an optional exit time and a blend duration. Scripts drive them with `SetFloat`, `SetBool`, `SetInteger` and `SetTrigger` in C++ or C#. Edit them in **Window > Animator**, a graph with draggable states, zoom and pan, right-click creation, and live state and parameter display during play.
- **Blend trees**: a state's Motion can be a 1D blend tree, which blends child clips by a float parameter and their thresholds. The two nearest children are mixed, children stay in sync by normalized time, and the loop length follows the weights. During play the Animator panel shows each child's weight. Crossfades work into and out of blend trees. **2D blend trees** place children at (X, Y) positions on two float parameters and weight them by gradient-band interpolation (freeform cartesian: any layout, exactly one child at its own position, every weighted child blended); the Animator panel draws the blend space with each child's weight, and outside play mode the blend point can be dragged to preview it. **2D Simple Directional** trees take one motion per direction (walk forward, back, left, right) and optionally one at the center (idle): the point's direction picks the two neighbouring directions and its distance blends toward the center.
- **Animator layers and masks**: a controller can have extra layers on top of the base layer. Each has its own states and transitions (sharing the controller's parameters and triggers), a weight, Override or Additive blending, and a mask of joints that covers each listed joint and its children (empty = whole body). Additive layers add their motion's change from its first frame. Edit them in the Animator window's Layers section (pick mask joints from the selected model's skeleton; while playing, a Live Weight slider). Scripts call `SetLayerWeight(layer, weight)`. Demo3D's 'Tentacle (Layers)' sways as a whole while its tip waves (`Animation/TentacleLayered.controller`). A **synced layer** (Sync) follows an earlier layer's state machine (its states, transitions, timing and crossfades) and plays its own motion for each of those states (e.g. a wounded version of every locomotion state); states without one play the source's motion.
- **Avatar Masks** (like Unity's AvatarMask): a `.mask` asset holding a list of joints (each with its descendants) that controller layers use in place of their own list: the Animator window's layer **Mask** picks one (or "this layer's own joints"), **Save As Asset** turns a layer's list into one beside the controller, and editing a picked asset's joints there saves the asset, so every layer and controller using it (an upper-body mask for all characters) takes the change at once. C++: `AvatarMaskAsset`, `AnimLayer::MaskAsset`, `AssetManager::GetAvatarMask` / `SaveAvatarMask` / `CreateAvatarMask`, `AssetType::AvatarMask`.
- **Sub-state machines**: states can be grouped (nested to any depth), and the graph shows each group as one node. Double-click it to open it, and use the breadcrumb or the Up node to go back. Transitions can target a group (they enter its Entry State), and a group can have its own transitions that fire from any state inside it. Right-click to create groups or move states into them. Demo3D's Tentacle keeps Wave and Curl in an 'Active' group. Each level has **Entry** and **Exit** nodes (as in Unity): Entry's transitions (right-click it) pick the state entered by their conditions, otherwise the default (the orange arrow); a transition to Exit leaves the group, taking the group's own transitions whose conditions hold, otherwise the parent level's Entry. Curl leaves the 'Active' group through Exit.
- **Foot IK** (like Unity's Foot IK with a ground-alignment script, built in): an Animator's **Foot IK** (humanoids, while playing) finds the ground under each foot with a ray from **Foot IK Reach** above the object's level (colliders that are not part of the object), moves the foot to stand on it as the animation stood on the level (its lift kept, so steps still leave the ground), lowers the hips when a foot must go lower than the leg reaches (the other knee bends), and tilts each foot to the slope (up to 40 degrees): walking up stairs and across hillsides without feet floating or sinking. C#: `Animator.FootIK`, `FootIKReach`; C++: `Animation::PlantFeet`.
- **IK from scripts** (like Unity's `OnAnimatorIK`): `Animator.SetIKPosition` / `SetIKPositionWeight` and `SetIKRotation` / `SetIKRotationWeight` give a humanoid's feet and hands goals (`AvatarIKGoal.LeftFoot`, `RightFoot`, `LeftHand`, `RightHand`, world space), and `SetLookAtPosition` / `SetLookAtWeight` turn its head (with neck and chest) toward a point; they hold until changed and apply after the pose each frame: each limb's upper and lower bone solved to reach (the elbow or knee bending toward its **hint**, `SetIKHintPosition` / `SetIKHintPositionWeight` with `AvatarIKHint.LeftKnee` ... `RightElbow`, else keeping its bend plane), then the hand or foot turned to the goal. Scripts overriding `OnAnimatorIK(layerIndex)` get it every frame before the Animator poses the object, the place to aim a hand at a door handle or plant feet on uneven ground. C++: `HumanoidIKGoals`, `Animation::ApplyHumanoidIK`, `AnimatorComponent::ScriptIK`.
- **Constraints** (like Unity's Position, Rotation, Scale, Parent and Aim Constraints, Add Component > Constraints): an object follows the weighted average of its **Sources** (other objects, each with a weight) every frame while playing, after animation and before LateUpdate, parents first so a constrained object's children come along. **Weight** blends from where the object rests (its pose when the constraint first applies) to the constrained pose, **Maintain Offset** keeps the offset it had from its sources then, and **Affect X / Y / Z** leave axes alone. Position adds an **Offset**, Rotation turns by one, Scale multiplies; **Parent** carries the object as if it were a child of each source (a sword switching hands by weights, a prop riding a moving object without reparenting); **Aim** turns its **Aim Axis** at the sources and its **Up Axis** toward the scene up, a **World Up Object** or that object's up (a turret, eyes, a spotlight following a target). C#: `PositionConstraint`, `RotationConstraint`, `ScaleConstraint`, `ParentConstraint`, `AimConstraint` (`ConstraintActive`, `Weight`, `MaintainOffset`, and the sources: `SourceCount`, `GetSource`, `SetSource`, `AddSource`, `RemoveSource`, as Unity's); C++: `Constraints::Update`.
- **Inverse kinematics**: an **IK Target** component on a target object pulls a joint (Tip) of an Animator's skeleton to the object's position after the animation is sampled, by turning the Chain Length joints above it: two joints solve exactly (law of cosines), bending toward an optional Hint object (elbow or knee direction); longer chains use cyclic coordinate descent. Weight blends it in, and Layer applies it after that Animator layer (scaled by the layer's weight) or after all layers. The Animator is the one set on the target or its nearest parent with one, so a hand or foot target can sit under the character. Demo3D's 'Tentacle (IK)' follows an orbiting orb. **Look At** mode turns the Tip joint so its Aim Axis points at the target instead (heads, eyes, turrets), shared evenly over Chain Length joints (neck and spine) and limited to Max Angle away from the animation.
- **Root motion**: with Apply Root Motion, the horizontal movement of the root joint (or Root Motion Joint) moves the object instead of the mesh: the pose stays in place, travel carries on across loop wraps, and switching clips does not jump. With a Character Controller the motion goes through it, so walk cycles collide and climb steps. Vertical motion stays in the animation.
- **Retargeting**: an Animator's **Animation Source** plays the clips of another model on this one's skeleton, matched by joint name (ignoring case and prefixes like `mixamorig:`). Rotations carry over as changes from each bind pose; root translation scales by the ratio of the skeletons' root heights, and the other joints keep the target's proportions, so one set of animations drives differently sized characters. **Humanoid avatars**: a model's joints are matched to the standard human bones (hips, spine, chest, upper chest, neck, head, shoulders, arms, hands, legs, feet, toes) by their names in any of the common conventions (Mixamo `LeftUpLeg`, Unreal `thigh_l`, Blender `thigh.L`, 3ds Max `Bip01 L Thigh`; twist, roll, end and finger joints left out); the model's Inspector shows its **Avatar** (Humanoid with the joint found for each bone, or Generic). With the Animator's **Retargeting** on Humanoid (the default) and both models humanoid, clips retarget through the human bones: each bone turns in the model's space as the source's turns from its **T-pose** (each rig's own, worked out from its bind pose by turning the arms out level, the spine up and the legs down in the rig's frame, so a rig bound in an A-pose and one bound in a T-pose share a reference), so rigs with other names, joint axes, extra joints and proportions play the same motion, the hips travelling scaled by the hips' heights; joints that are no human bone (fingers, tails) still match by name. **Muscle limits** (the Animator's **Muscle Limits**, on by default) keep each human bone within a human range of motion from the T-pose, measured relative to its parent bone as Unity's muscles are: swing forward / back and to the side, and twist about the bone (spine and neck ±40°, upper arms -80..140° forward and -100..120° up, hips -50..130° forward, knees bending only backward to 160°, elbows and wrists limited in how far they bend whichever way the rig bends them), so a clip made for another figure cannot hyperextend a knee or spin a head round; a clamped bone carries its children along and motion within range is unchanged. C++: `Animation::MapHumanoid`, `HumanoidMap`, `HumanBone`, `Animation::RetargetHumanoid`, `Animation::HumanMuscleLimit` / `ClampMuscle`, `AnimatorComponent::Retargeting` / `MuscleLimits`; C#: `Animator.Retargeting`, `Animator.MuscleLimits`.
- **Animation clip assets** (`.anim`, like Unity's AnimationClip assets): editable skeletal clips holding keys for the joints of a model's skeleton, by joint name (so they survive the model being re-imported), with the model they were made for. Animators on that model (or using it as their Animation Source, retargeted like its own clips) play them by name next to the model's clips, and one named like a model clip replaces it, so an edited copy of "Walk" plays wherever "Walk" did. **Window > Animation** edits them for the selected object's Animator: pick one of its model's `.anim` clips, **Extract** a copy of one of the model's clips or start a **New** one, and see every joint as a row of keys under a time ruler (click or drag the ruler to scrub; drag keys along a row to move them, right-click one to delete it). **Preview** poses the object at the current time (its Animator is put back afterwards, and before play or saving). The selected joint's rotation (degrees) and position at the current time are shown, and editing them keys them there; While previewing, the Scene view draws the skeleton (click a joint to select it) with a **rotation gizmo** on the selected joint: turning it keys the joint's rotation at the current time, so poses are set by hand. **Key** records the joint's current pose (Ctrl / Shift clicking rows selects several joints: **Key Selected** keys them all, **Delete Key** removes theirs and dragging a key moves theirs together; **Key All** keys the whole pose), **Delete Key** removes it, and the joint's keys join as **Linear**, **Step**, **Smooth** (automatic tangents, each key's slope from its neighbours) or **Free** curves (tangents set by hand); a curve view under the keys draws the joint's rotation (Euler degrees) and position over the clip: click a key on it to select it (and go to its time), and a smooth key shows **tangent handles**: dragging one sets the curve's slope there (both sides together, Alt for one side only, a broken tangent), with the key's value and its in / out slopes per second shown, and right-clicking a key sets its tangents back to **Auto** or **Flat**. Hand-set tangents are saved with the clip and survive key edits (a new key gets an automatic tangent, moved and removed keys take theirs along); the clip's length and name edit in place. Edits reach Animators at once and are saved to the file. A model with **blend shapes** gets a row per shape under its joints: select one to see its weight (0..100) at the current time, where changing it (or **Key**) keys it, and drag or right-click its keys like a joint's; they are saved as channels named after the shapes (`blendShape:<name>`), so they play on any model with shapes of those names, **Extract** keeps a model clip's shape animation, and previewing puts the renderer's own weights back afterwards. **Object properties** (like Unity's clips keying any component field): **+ Property** lists the object and everything under it, with each component's numeric fields (floats, vectors, colors, bools and ints as numbers); picking one keys its current value at the current time and gives it a row, where selecting it shows its value at the current time (changing it keys it, **Remove** stops animating it). Properties and blend shapes have the same **curve view** and interpolation modes as joints: a property's values (up to four, x red, y green, z blue, w grey) or a shape's weight (0..100) over the clip, with the selected key's tangent handles to drag. They are saved as channels named by path, component and field (`property:Lamp/Bulb|Point Light|Intensity`), carry over when the clip is retargeted, and an Animator playing the clip writes them every frame while the game runs (a light flickering, a door's color, a child's position); previews in edit mode leave the scene's values alone. **Record** (like Unity's record mode, next to Preview, which it turns on): while it is on, the clip's properties show on the objects at the current time, and anything changed on the object or the objects under it, in the Inspector or with the Scene view's tools, is keyed there (a new property row when it was not animated yet); leaving record mode (or the preview) puts their values back as they were before recording, so the scene keeps its own and the clip has the motion. **Keyframe reduction** (like Unity's animation compression): a model's import settings have **Reduce Keyframes** with a **Rotation Error** (degrees) and **Position Error** (meters), dropping the keys of linear channels that the line between the remaining keys passes within them (Ramer-Douglas-Peucker, so every original key stays within the error: the Sandbox's Tentacle keeps 210 of its 450 keys at the defaults), and the Animation window's **Reduce Keys** does the same to a `.anim` clip's linear channels (a recorded one). C++: `Animation::ReduceKeys`, `AnimationClipAsset::ReduceKeys`, `MeshImportSettings::ReduceKeyframes`. **Animators without a skeleton** (like Unity animating any object): an Animator on an object with no skinned model (a door, a light, a sign; no Mesh Renderer needed) plays **generic** `.anim` clips, those made for no model, by name or from controller states: their property channels and events work as on characters, and the Animation window edits them for such an object (no joint rows; **New** puts clips in `Assets/Animations`). **Onion Skin** draws, while previewing, the skeleton a few steps before (red) and after (green) the current time in the Scene view, fainter farther off (the spacing and how many on each side are set beside it; looping clips wrap), to see the motion around a pose while keying it. **Animation events** sit on the clip itself (like Unity's): **+ Event** adds one at the current time on an Events row above the joints (drag a marker to move it, right-click to delete it; select it to name its function or type its time); they are saved in the `.anim` and kept when it is retargeted onto another model, and whenever an Animator's playback of the clip passes one (directly or in a controller state, across loop wraps) scripts on the object get `OnAnimationEvent(function)`, as with a state's events. Selecting a `.anim` in the Project window shows its model, name, length and key count. C++: `AnimationClipAsset` (`FromClip` / `ToClip`, `SetKey` / `MoveKeys` / `RemoveKeys`, `SetTangents` / `AutoTangent` / `FlatTangent`), `AssetManager::GetAnimationClip` / `SaveAnimationClip` / `CreateAnimationClip` / `ClipsFor`, `AssetType::AnimationClip`.
- **Animation events**: states list events at normalized times. When playback passes one, `OnAnimationEvent(name)` is called on the entity's C++ and C# scripts (looping states fire every loop). Demo3D's "Tentacle (Blend Tree)" sweeps Sway, Wave and Curl with a script-driven parameter and squashes on a "Pulse" event.
- **Timelines** (cutscenes and scripted sequences, like Unity's Timeline): a `.timeline` asset (Project > Create > New Timeline) holds tracks that animate any numeric field of any component (positions, rotations, light intensities, colors, material values) on the object with the **Timeline** component or on objects under it by name path, each with Smooth, Linear or Step keys, plus events that call `OnAnimationEvent(name)` on the object's scripts. It plays on awake or from scripts (C#: `Timeline.Play()`, `Stop()`, `Time`, `Speed`, `Loop`), looping or stopping at the end. **Window > Timeline** edits the selected object's timeline: Preview scrubs the scene through it (undone afterwards), Key records a field's current value at the current time, keys drag along each track's strip, the selected key's time and value are editable, tracks can be muted, and Add Track lists the object's and its children's numeric fields.
- **Timeline clip tracks**: besides property tracks a timeline can have **Activation** tracks (an object under the timeline is active only during its clips), **Audio** tracks (each clip plays an audio clip through the object's Audio Source, from Clip In seconds, stopping at the clip's end) and **Animation** tracks (each clip plays one of the Animator's animation clips at its Speed, looped or held, overriding the Animator's own clip and controller; overlapping clips crossfade, and after the last clip its final frame holds). In **Window > Timeline**, clips are colored bars to drag (and resize by their right edge), with Start, Length, Clip In and the clip's content in the selected-clip editor and **Match Length**. A **curve view** under the tracks draws the selected property track's channels over time (one color per channel); drag a key up or down to change its value, with Shift also along time.
- **Nested timelines**: a **Control** track's clips each play another timeline on the track's object (cutscenes built from shots, a door sequence reused in several scenes): the nested timeline's tracks resolve from that object, from Clip In at the clip's Speed, looping over the clip or holding its end, and its events and audio fire as it plays. Nesting goes up to 8 levels (a timeline that plays itself stops there). In Window > Timeline the clips show the nested timeline's name, and Match Length fits a clip to it.
- Fonts: TTF/OTF assets baked to **multi-channel signed distance field** (MTSDF) atlases with msdfgen from stb_truetype's outlines (Latin-1), and an embedded default font, so text works with no assets. The median of the three color channels is the distance to the outline with its corners kept sharp (alpha holds the plain distance); the UI and sprite shaders turn it into an edge about a pixel wide at any size, so huge titles and close-up 3D text stay crisp, corners included. Meshes include built-in primitives and glTF/GLB/OBJ import.
- **OBJ materials**: an OBJ's `mtllib` is read: each `usemtl` group becomes a sub-mesh with its material (Kd color, d/Tr opacity, Ns shininess as roughness, Ke emission, and map_Kd, map_Bump and map_Ke textures), editable and extractable like a glTF model's.
- **glTF materials** are imported with the model: base color, metallic/roughness, normal and emissive maps and factors (including `KHR_materials_emissive_strength` and the base-color `KHR_texture_transform`), alpha mode (opaque, mask, blend) and double-sided. Each primitive becomes a sub-mesh drawn with its own material. Until extracted, the materials and their embedded or external textures are read-only sub-assets of the model; **Extract Materials** in the model's Inspector writes them out as `.mat` assets plus textures (normal and metallic-roughness maps imported as linear). A Mesh Renderer's Material overrides every part, and its **Materials** list overrides single slots: slot N replaces the model's material N (or sub-mesh N for models without materials), and empty slots fall through to Material or the model's own. **Match Mesh Slots** in the Inspector sizes the list to the mesh (hover it for the slot names). Alpha-cutout materials also cut their shadows. The sample `Models/Showcase.glb` shows each material type.
- GPU entity-ID buffer for click selection, an editor grid, gizmo lines and billboard icons for cameras, lights and audio sources.

**Editor**
- Docking layout that is saved per project, a play-mode tint, a scene-view orientation cube, plus a toolbar with Move, Rotate and Scale tools (ImGuizmo), Local/Global mode, 2D mode and a grid toggle.
- **Multi-select**: Ctrl/Shift-click in the Hierarchy, Ctrl-click in the Scene view. Delete, duplicate, copy/paste and the transform gizmo act on the whole selection, and the Inspector shows only the components all selected objects share; edits, Reset and Remove apply to all of them. Values that differ across the selection show as `--`: per axis for vectors, a dash in checkboxes, and `--` for names, enums, assets, entity references and colors (next to the active object's swatch). Editing one axis of a vector changes only that axis on every object, so dragging Position X keeps each object's own Y and Z. The header (active, name, tag, layer) multi-edits the same way.
- **Component clipboard**: right-click a component header (or its "..." button) for Copy Component, Paste Component Values and Paste Component As New. Values go through the OS clipboard as JSON, so they paste across scenes and editor instances.
- **Mixed values** in multi-object editing also cover curves, gradients and lists: a `--` note says they differ (editing applies the shown value to all). Lists of the same length mark each differing element with `--` instead, and editing one element changes only that element on every selected object.
- **Component order**: the same menu has **Move Up** and **Move Down**. Each object keeps its own Inspector order (saved with the scene, undoable, and recorded as a prefab override); Transform always stays first, and newly added components go to the end.
- **Edit > Preferences** (per user, `%APPDATA%/Dimension/EditorPreferences.json`): **theme** (Dark, Light or Midnight) and accent color, UI scale, scene camera speed and field of view, grid, clear console on play, save scene before play, and an autosave interval that backs the open scene up to `.dimension/Autosave` without touching the scene file.
- **Prefabs**: instances stay linked to their `.prefab` asset. Per-field overrides show in blue in the Inspector, and the prefab header offers **Apply**, **Revert**, **Unpack** and **Select**. Changes to the asset (Apply, or edits on disk) reach every instance without touching their overrides. Added and removed components and children propagate too. The root's position, rotation and name belong to the instance, as in Unity.
- **Prefab variants**: right-click a prefab in the Project panel > **Create Prefab Variant**. A variant stores only its differences from its base (changed fields, added or removed components and objects), so edits to the base reach the variant and its instances wherever the variant does not override them. Edit a variant in Prefab Mode or Apply from one of its instances and only the differences are saved; variants of variants work too, and the Inspector names the base ("Variant of"). The sample `Prefabs/Gold Ball.prefab` is a gold, bouncier variant of `Ball.prefab`, spawned by Demo3D's Spawn Ball button.
- **Nested prefabs**: an instance of one prefab inside another (dragged in, in Prefab Mode or before Create Prefab) is saved as a reference to the inner prefab plus that instance's own changes, so editing the inner prefab updates every prefab that contains it and all their instances, while each nested instance keeps its overrides, place and name. Nesting goes any number of levels deep (a wheel in a cart in a train); a prefab that would contain itself is refused at load. The Inspector names the nested prefab of a selected part and opens it.
- **Apply to Nested**: a part of a nested instance shows its inner prefab in the Inspector with **Apply to Nested**, which writes that instance's changes (fields, components and added objects) into the inner prefab itself, so every prefab using it changes; the instance's overrides there are cleared.
- **Prefab Mode**: double-click a prefab in the Project panel (or click **Open** in the prefab header or the asset's Inspector) to edit it on its own, in a stage lit by a neutral studio light. A breadcrumb bar over the Scene view leads back to the scene. Auto Save (on by default) writes the asset when each edit finishes; with it off, Save or Ctrl+S writes it, and leaving asks first. The scene keeps its unsaved changes, undo history, selection and camera, and its instances update on return without losing their overrides. Objects outside the prefab root are not saved, a prefab cannot contain itself, and Play leaves Prefab Mode first. `--prefab <path>` opens one on startup.
- **Hierarchy**: drag-and-drop parenting and reordering, rename, duplicate, delete, create menus, and "Create Prefab". The **search** box filters it to a flat list of matches (like Unity's): every word must match, a plain word part of the name, `t:Rigidbody` (or `t:MeshRenderer`, or a script class) a component the object has, `tag:Player` its tag; Select All picks them all, double-click frames one, and hovering shows where it sits. While searching, the **Scene view dims** every mesh but the matches (the editor's `--search "t:Rigidbody"` starts with a search).
- **Inspector**: reflected component fields, Add Component search, script class picker with public fields, texture import settings, model import settings (scale, whether to import animations and materials, and which clips; cached per setting), and a material editor.
- **Scene view**: Unity-style camera, GPU picking, transform gizmos, and dropping assets in to create objects or instantiate prefabs.
- **UI rect editing**: outside play mode, the selected UI Rect shows its outline, pivot and eight handles in the Game view. Drag inside to move it, drag an edge or corner to resize it (only that side moves, whatever the anchors and pivot; Ctrl snaps to 10 units), and click a widget there to select it. Changes are undoable and record prefab overrides; children of a layout group show their outline only.
- **UI in the Scene view**: the canvases show in the Scene view (toolbar toggle **UI**) on the XY plane from the origin, 100 pixels a unit, at the Game view's size, drawn over the world as an image of the UI itself (exact colors). Click a UI element there to select it, drag it or its handles to move and resize it as in the Game view (undoable, recording prefab overrides); framing (F) a UI element or a Canvas frames its rectangle on that plane, and the transform gizmo stays off UI elements. C++: `SceneRenderer::RenderUIOnly`.
- **World Space canvases**: a Canvas's new **Render Mode** World Space makes it a panel on its object in the 3D world (**Pixel Size** pixels laid out, **Pixels Per Unit** of them a meter, centered on the object facing its +Z): its UI is drawn into an image each frame and shown with depth (objects in front hide it), and the pointer reaches it through the main camera's ray, so buttons, sliders, toggles and fields on it work as on the screen (and the pointer counts as over UI there). Pointer events (OnPointerEnter / Exit / Down / Up / Click, drags and drops, with positions in the panel's pixels) reach scripts on its elements too. Instead of the mouse, a script can point at World Space canvases with a ray of its own, a VR controller or a crosshair: `EventSystem.SetPointerRay(origin, direction, pressed)` (its `pressed` acting as the button, working without a mouse) until `EventSystem.ClearPointerRay()` (sample: the Demo3D Player's `LaserPointer`, L to turn it on and F to press, on the kiosk panel). Several rays work at once, one per `pointerId` (a VR controller in each hand): each hovers, presses, clicks and drags on its own (a button or slider held by one is released only by it), pointer events carry `PointerEventData.PointerId` (-1 the mouse), each ray draws a dot where it meets a panel (`showCursor`), and `ClearPointerRay(id)` stops one (what it was over gets its Exit). Keyboard and gamepad navigation go to the canvas holding the selection: on a World Space panel the arrows / D-pad move between its widgets and, with nothing further that way, on to the nearest other panel that way on screen (entering at its near side), Submit presses there, and the highlight is drawn on that panel (sample: `KioskFocus`, K / Y selecting the kiosk's button, next to a second panel). C++: `Scene::CanvasOf`, `UI::NavigationEntry`, `CanvasRenderMode`, `CanvasComponent::PixelSize` / `PixelsPerUnit` / `WorldSize`, `UI::ComputeLayout` / `Update` / `BuildDrawList` / `ElementsAt` for one canvas, `UI::WorldCanvasPoint` / `WorldCanvasRayPoint`, `Scene::SetUIPointerRay` / `ClearUIPointerRay` / `UIPointerCursors`, `UI::PointerState::Id`. In the Scene view, a World Space canvas's elements are selected, moved and resized with the same rect handles on the panel itself, and framing one frames its panel.
- **UI Mask** (like Unity's Mask and RectMask2D): a new **UI Mask** component clips its children (and theirs) to its rect, for drawing and for the pointer alike, or with **Shape** Image to its UI Image's shape (the texture's alpha: round portraits, rounded panels), with edges faded over **Softness** pixels (horizontal, vertical); **Show Mask Graphic** off hides the mask's own image. Masks nest: a mask inside another clips to both rects, and up to four soft or image-shaped masks above an element multiply (a soft-edged list inside a round frame). Soft edges and image shapes are applied per pixel in the UI shader from a per-frame table of masks. C#: `UIMask` (`Shape`, `Softness`, `ShowMaskGraphic`). Sample: Demo3D's round CRATES badge and a news ticker (`TickerScroll`) fading in and out at the edges of its mask.
- **UI Layout Element and Content Size Fitter** (like Unity's): a **UI Layout Element** sets how a child sits in its parent's UI Layout Group: **Preferred Size** and **Min Size** override its size there (-1 unset), **Flexible Size** weights share out the group's leftover length (a column of a header, a body that fills, a footer), and **Ignore Layout** leaves it where its own anchors put it. A **UI Content Size Fitter** sizes a rect to its content along either axis (about its pivot): a UI Text to its lines (rich-text tags take no room; with only the height fitted, it wraps at the rect's width and grows a line at a time), a layout group to its children plus padding, also when that rect is itself inside a group. Groups use these sizes; children without either keep their Size, so existing layouts are unchanged. Sample: Demo3D's "Balls in play" chip, whose background grows with its count.
- **UI style sheets and classes** (like UI Toolkit's USS): a `.uistyle` asset (Create > New UI Style Sheet) lists classes of component values (`{"classes": {"title": {"UI Text": {"Font Size": 40}}}}`: any registered component and field), and a **UI Style** component gives an element its **Classes** (space-separated, later ones win) and a **Sheet** (or takes the nearest parent UI Style's, so a canvas names the sheet once). Styles apply when the classes or the sheet change: an edited sheet restyles the scene at once, a class removed takes its values with it (they go back to what they were), and scripts can still change styled values in between. C#: `UIStyle.Classes`, `AddClass` / `RemoveClass` / `ToggleClass` / `HasClass`. **Selectors:** `"types"` rules apply to styled elements by component (`"UI Button"`), and a `name:hover`, `:pressed`, `:selected` or `:disabled` rule (a class's or a type's) applies while the element is in that state (state rules after plain ones, types before classes). A rule's `"transition"` (seconds) eases the numeric fields it sets, colors, sizes, positions, in and out again (smoothstep), from wherever they are mid-way. **Transitions:** a UI Button's tint now fades between its normal, hover, pressed and disabled colors over its **Fade Duration** (0.1 s by default, like Unity's Color Tint). Sample: `Assets/UI/Kiosk.uistyle` styles the Demo3D kiosk, whose button grows smoothly under the pointer (`accent:hover` with a transition) and turns green and back on each click (`StyleToggle`).
- **Input methods (IME)**: typing Chinese, Japanese or Korean into a UI input field through the system's input method shows the text being composed inside the field at the caret, underlined and with the input method's own cursor, while editing keys go to the input method; what it commits is typed into the field as usual. The input method's candidate list opens beside the field's caret (in the Player, and in the editor's Game view while playing), and the system's separate composition window stays hidden while a game field has the focus. Single-line fields show the composition; multi-line fields take the committed text. C++: `Input::GetComposition` / `SetComposition` / `SetTextInputRect`, `UIInputFieldComponent::Composition` / `CaretRect`; the Player's `--ime text` simulates a composition for automated checks.
- **Kerning and combining marks**: text is positioned by each font's GPOS table: **kerning** pairs (single glyph pairs and class pairs, through extension lookups, as Segoe UI and Arial store them; the `kern` table for fonts without) tighten pairs like "AV" and "Wa" between neighbouring characters of one font and size, and **combining marks** (accents, Vietnamese stacks, vowel signs) are placed on their base by the font's mark-to-base anchors and take no room. A mark the font lacks brings its base from the same fallback font, so "e" + U+0302 + U+0323 draws as one "ệ" rather than an accent floating beside the letter. C++: `StyledChar::Kern` / `MarkOffset`.
- **Unicode text, fallback fonts and right-to-left scripts**: fonts are no longer limited to Latin-1. Any character a font has is baked into its distance-field atlas the first time text uses it (the atlas goes up again at most once a frame), and characters it lacks come from **fallback fonts**: by default the system's (on Windows Segoe UI for Greek, Cyrillic, Arabic and Hebrew, Segoe UI Emoji, Segoe UI Symbol, Microsoft YaHei for Chinese and Japanese kana, Malgun Gothic for Korean, Nirmala UI for Indic scripts), loaded on first need without baking anything up front; `Font::SetFallbackFonts` sets your own. **Arabic** is shaped (each letter in its isolated, initial, medial or final form, lam-alef ligatures, harakat kept out of the joining), and **bidirectional** lines are reordered for display: a paragraph takes its first strong character's direction, Hebrew and Arabic runs read right to left, numbers and Latin words inside them stay left to right, and brackets mirror. UI Text, world-space Text and input fields all use it. **Color emoji**: fonts with color glyph tables (COLR layers with a CPAL palette, as Segoe UI Emoji has them) bake each emoji the first time it is used into a second atlas of plain sRGB colors, its layers rasterized and stacked in their palette colors (fonts with **COLR version 1** paints, as Windows 11's Segoe UI Emoji has them, are drawn from those: layers of glyph outlines filled with solid colors and linear, radial and sweep gradients, under affine, translate, scale, rotate and skew transforms, and composited, so the Fluent emoji keep their shading and gradients; `ColrV1::Render`), and draw it untinted (the text's alpha and a `<color>` tag's alpha still fade it); emoji runs are **shaped** by the font's own glyph substitutions (GSUB: its ccmp/liga lookups, with single substitutions, ligatures and chaining contexts), so skin tones (👍🏽), professions (👩🏾‍💻), couples and flags like 🏳️‍🌈 join into the font's single glyphs as Windows draws them, and variation selectors and leftover joiners take no room. C++: `Font::GetColorAtlasIndex`, `Glyph::Color`, `TextQuad::ColorGlyph`, `Font::kGlyphIndexBit`. Sample: the Sandbox's menu string table now has Arabic and Hebrew (Demo2D's language button, or `--system-language ar`).
- **UI data binding** (like UI Toolkit's runtime bindings): a **UI Binding** component ties its element's widget to a script field, C# or C++, by **Path** (`Script.Field`, or just the field) on a **Source** object (or the element or its nearest parent with that script). A UI Text shows the value through **Format** (`"Score: {0}"`, `{0:F1}` for one decimal); a slider, toggle, input field or dropdown shows it and, **Two Way**, writes the player's changes back to the field (C# fields go to the live object). Values flow in only when they change, so bound texts cost nothing while still. C#: `UIBinding` (`Path`, `Format`, `TwoWay`). Paths go into a field's value too (`Player.Stats.Health`, `Inventory.Items.0.Name`), and a write changes just that part. A path can also name a C# property (read-only ones too) or a method: a method with no parameters gives the value, and a widget writes through a property's setter or a method with one parameter. Sample: Demo3D's Settings panel binds a label and a slider to the C# Spinner's `BobHeight`.
- **UI List View** (like UI Toolkit's ListView): on a scroll view, it shows a list from a script field (an array or `List<T>`, of values or [Serializable] classes) as rows cloned from a **Row Template** (an element kept inactive), **Row Height** plus **Spacing** apart. Only the rows in view exist: scrolling hands the same rows the next items, so a list of thousands costs a screenful. Each row's UI Bindings read `item`, `item.Field`, `index` and `number` (index + 1), and a row's input field, toggle or slider writes its item back into the list. Sample: the Demo3D leaderboard panel (C# `HighScores`, a new score every two seconds slotting into place, its heading bound to the `Count` property).
- **Game view**: renders the primary camera. **Play/Pause/Step** run on a cloned scene, and edits made while playing are discarded on Stop.
- **Project** browser: folder tree, thumbnails and material swatches, New Material/Scene/Folder, search, rename, move by drag, delete, and import by dropping files from Windows Explorer.
- **Console** with level filters, collapsing and clear-on-play. Also **Scene Settings**, **Stats**, and **Project Settings**.
- **Profiler** (Window > Profiler, like Unity's CPU Profiler): the last 300 frames as stacked bars of their top-level sections (waiting for the GPU, update, editor UI, render, submit; the rest of the frame grey) against 60 and 30 fps lines, scaled so a rare hitch such as loading runs off the top; the median and slowest frame times. Click a frame to pause on it: its sections nested (scripts, systems, navigation, fixed update and physics, animation, particles and audio inside the update; each view and its render list inside the render) with milliseconds, share of the frame and calls, and its counters (draw calls, triangles, meshes, occluded). Engine and game code time their own sections with `DIM_PROFILE_SCOPE("Name")`. The **GPU** side lists the time of each render pass (shadows, depth prepass and SSAO, opaque, effects and post processing with the transparent pass inside, each view, the editor UI) from timestamp queries, read back once the GPU has finished that frame (so it lags a frame or two). **Memory** shows the GPU memory the engine's images and buffers take (textures, render targets, mesh buffers, other buffers: counts and MB) and the device's video and system memory heaps against their budgets.
- **Frame Debugger** (Window > Frame Debugger, like Unity's): while enabled, the Scene or Game view's frame as a list of its draws under their passes (shadows, depth prepass, opaque meshes, sky, sprites, particles, transparent meshes, decals, UI), each with the target it draws into, what it draws (the mesh), its object, triangles and instances. Picking a draw, or stepping with the arrows or slider, shows the view as it stood right after it (later draws left out, effects and post processing still applied), with the later rows greyed; Select Object (or a double click) selects the draw's object. A mesh draw shows its material values (kind, blend mode, base color, metallic and roughness, emission, normal map strength, alpha cutoff), and **Show Target** pictures the target as the draw left it: the shadow map atlas (its cascades) or the point shadow atlas in grey, near bright, or the HDR image tonemapped. `--open "Frame Debugger" --frame-event N` starts the editor stopped at draw N.
- Copy/paste of GameObjects through the OS clipboard, snapshot-based **Undo/Redo**, scene save/load in JSON, unsaved-change prompts, and **File > Build Settings** (Ctrl+Shift+B): an ordered list of scenes in the build (drag scenes in; scene 0 starts the game), product name, window size, fullscreen and VSync, an **Icon**, **Strip Unused Assets** (on by default: only assets the build scenes reach through scenes, prefabs, materials, controllers and models ship, plus everything in `Assets/Resources`; glTF buffers and images and OBJ material files come along), an output folder, and **Build** / **Build And Run** (Ctrl+B).
- **SceneManager**: scripts switch scenes with `SceneManager::LoadScene("Name")` or a build index (C#: `SceneManager.LoadScene`). Loads apply at the end of the frame, in the Player and in editor play mode (Stop returns to the edited scene). Sample scripts `LoadSceneButton` and `LoadSceneAfterDelay`; Demo3D and Demo2D link to each other.
- **Several scenes at once**: loads go into the running scene. `LoadSceneMode::Single` (the default) destroys every object not marked persistent and takes over the new scene's name and settings. `LoadSceneMode::Additive` adds a scene's objects; loading the same scene twice gives the second copy new ids. `SceneManager::UnloadScene("Name")` removes the root objects a scene contributed. `GetScene().DontDestroyOnLoad(entity)` (C#: `SceneManager.DontDestroyOnLoad(entity)`) keeps an object's whole root hierarchy, and its script instances and state, across single loads. `Scene::GetLoadedScenes()` / `SceneManager.LoadedSceneNames` list what is loaded, with persistent objects under "DontDestroyOnLoad". Demo3D's music uses the sample `KeepAcrossScenes` script, so it keeps playing through 3D -> 2D -> 3D, and the copy that comes back with Demo3D removes itself. Physics gravity stays as it was when play started.
- **Asynchronous loading**: `SceneManager::LoadSceneAsync(name)` (C#: `SceneManager.LoadSceneAsync`, returning an `AsyncOperation`) reads and parses the scene on a worker thread and decodes the textures and models it uses (through prefabs, materials and controllers) into a prefetch cache, while the current scene keeps running. The scene activates at the end of a frame on the main thread, where GPU uploads use the prefetched data. `Progress` runs to 0.9 in the background and 1 when active; setting `AllowSceneActivation` to false holds a ready scene (e.g. behind "press any key"). Demo3D's "2D Demo" button loads asynchronously (`LoadSceneButton` with Async on).
- Shipped games use `DimensionGame.exe` (renamed to the product name): no console window, `Player.log` next to the executable, borderless fullscreen with Alt+Enter, and the project's window size and VSync. `DimensionEditor --build <folder>` builds headlessly (exit code 0 on success) for CI.
- **Application icon**: the editor, player and game executables carry the engine's icon (`Engine/Resources/Dimension.ico`, also used for their windows). Build writes the project's Icon (any image; square, 256 px or more looks best) into the game's executable at 16 to 256 px, so Explorer, the taskbar and the window show it, and the player also sets it as the window icon. The Sandbox uses `Sprites/GameIcon.png`.

**Particles**
- The Particle System component covers duration and looping, randomized start lifetime, speed, size, rotation, spin and color, gravity and drag, rate-over-time and burst emission, and cone, sphere, box or point shapes in local or world space.
- **GPU particles**: with Simulate On GPU, a compute shader creates and moves the particles in a fixed ring of Max Particles slots (up to a million per system), and a vertex shader draws them straight from that buffer as camera-facing quads, so the CPU only counts what to emit. It supports the main module, emission, shapes, color, size and speed over lifetime, force over lifetime, curl noise, plane collision, the texture sheet and **trails** (velocity over lifetime stays CPU-only; a GPU system can still be a sub emitter's target). GPU trails keep 8 recorded positions per particle (for systems of up to 262,144 particles) and draw as the same tapering, fading ribbons as CPU trails, straight from the GPU buffers. `Scenes/Particles.scene` runs a fountain, a swirling nebula and embers: 1,000,000 particles in about 3 ms per frame (Debug build).
- **GPU particle collision**: with Collision set to World, GPU particles collide with what the camera saw in the last frame (its depth buffer): they bounce off the visible side of surfaces with the system's Bounce and Dampen, while particles off screen or behind objects pass freely, as screen-space collision does.
- **GPU particle sorting**: with GPU Sorting on, alpha-blended GPU particles draw back to front. For each view a compute pass writes every live particle's distance to the camera, a bitonic sort orders them on the GPU, and the vertex shader reads the particles in that order, so smoke and dust layer correctly without a CPU readback (500,000 particles sort in about 4.5 ms in a Debug build).
- **GPU particles and colliders**: with **Collide With Colliders**, GPU particles also bounce off the 32 sphere, box and capsule colliders (and characters) nearest the emitter, moving ones included, with the system's Bounce, Dampen and Lifetime Loss, so rain leaves dry ground under a ball and runs off a tilted plank.
- **Mesh emission**: the **Mesh** shape starts particles at random points on a mesh's surface (the object's Mesh Renderer mesh, or **Shape Mesh**), more where it has more area, moving out along its normals, for CPU and GPU systems alike (glowing embers coming off a model, dust from a statue). The spawn points are 4,096 area-weighted samples per mesh, made once and shared.
- **Collision decals**: with **Collision Decals**, each particle that collides (CPU systems, and GPU systems colliding with the depth buffer, colliders or the ground plane, whose first impacts each frame are read back from the GPU) leaves a mark on what it hit at its first impact (paint, blood, scorch marks), Decal Size across, in its color, turned at random, fading over the last third of Decal Lifetime, at most Max Decals at once, drawn through the decal pass.
- **Color over Lifetime** (a Gradient), **Size over Lifetime** and **Speed over Lifetime** (Curves). Curve and Gradient are reflection field types with inline editors: drag keys, double-click to add (or to pick a gradient key's color), right-click to remove. A curve key's right-click menu also sets its **tangents**: Auto (monotone), Free (one slope, dragged by its handles), Broken (separate in and out slopes) or Flat; hand-set tangents make the curve smooth and save with it.
- **Smooth curves**: tick Smooth under any curve for a monotone cubic through its keys (tangents chosen automatically and flat at peaks, so it eases in and out without overshooting a key). Plain curves still save as a key list.
- **Velocity over Lifetime** adds a velocity (local or world space, scaled by a curve) that moves particles without accumulating, plus an **Orbital Speed** around the emitter's Y axis. **Force over Lifetime** adds an acceleration (wind, thrust; local or world, scaled by a curve) that builds up velocity like gravity.
- **Collision** against a ground plane or, in play mode, the 3D physics colliders, with bounce, dampen and lifetime loss.
- **Texture sheet animation**: a particle texture can be a grid of frames (columns x rows, optionally only the first N) played over each particle's life, any number of cycles, optionally from a random start frame. **Noise** adds swirling curl-noise drift (strength, frequency, scroll speed). Curl noise is divergence-free, so particles swirl without bunching up. Demo3D's campfire smoke uses a generated 4x4 smoke flipbook (`Sprites/SmokeSheet.png`) with noise, and the flames flicker with noise.
- **Sub-emitters**: another Particle System bursts at each particle's birth, collision or death (fireworks).
- **Trails**: tapering, fading ribbons behind each particle.
- **External forces**: a particle system's **External Forces** (per second) makes its particles take up the wind of the Wind Zones around them (CPU systems): smoke and leaves drift with gusts.
- **Particle lights** (like Unity's Lights module, CPU systems): with **Lights**, **Light Ratio** of the particles (the same ones all their life) carry a point light, at most **Max Lights** per system: **Light Color** times the particle's color (**Use Particle Color**), **Light Intensity** times its alpha so it fades out with it, **Light Range** meters (times its size with **Size Affects Range**). Sparks, embers and fireflies light what is around them.
- Particles render with alpha or additive blending, using a texture or the built-in soft particle; HDR start colors glow with bloom. Demo3D has fireworks (death sub-emitter + trails) and a spark fountain bouncing on the physics ground.
- Particles are camera-facing quads sorted with sprites. They preview live in the editor, the emitter shape is drawn when selected, and scripts can call `Play`, `Stop`, `Emit` and `Clear`.

**Lines and trails**
- **Line Renderer** (GameObject > Effects > Line): a polyline drawn as a joined, mitered ribbon. Positions can be local or world space, optionally looped, with a width curve and color gradient along the line. The ribbon faces the camera or lies flat facing the object's Z axis, and takes a texture that stretches or tiles every world unit, with alpha or additive blending. The Inspector edits the point list (count, per-point XYZ, remove), and the selected line shows a handle at each point. The same handles edit the points of a **Terrain Path** and a **Path Placer**: click one to move it with a gizmo (undoable), Shift-click a segment to insert a point, Delete to remove the picked one.
- **Caps and joins**: Corner Vertices rounds the joins (square-ended segments with a fan around each corner, instead of miters) and End Cap Vertices rounds the ends of open lines, on Line and Trail Renderers alike.
- **Scene-view point editing**: with a Line Renderer selected, its points show as handles in the Scene view; click one to move it with its own gizmo (Ctrl snaps, undoable), click elsewhere or press Escape to return to the object's gizmo. Shift-click on a segment inserts a point there, and Delete removes the picked point (a line keeps at least two).
- **Trail Renderer** (GameObject > Effects > Trail): records the object's world position while playing (every Min Vertex Distance) and fades points out after Time seconds, with width and color over the trail's age. Scripts can toggle `Emitting` and call `Clear()`.
- Both batch with sprites and particles. Demo3D has a trail on the orbiting moon, a gradient arch whose shape is rebuilt every frame by the C# `LineWave` script, and a ring lying flat around the campfire.

**UI (screen space)**
- Canvas with constant-pixel or scale-with-screen-size modes, and a UI Rect with Unity-style anchors, pivot, position and size.
- UI Image (simple or 9-sliced), UI Text (word wrap, horizontal and vertical alignment) and UI Button (hover and pressed tints). A click calls `OnClick()` on the button's scripts.
- **Rich text** (UI Text and Text (3D), on by default): `<b>`, `<i>`, `<u>`, `<s>`, `<color=#ff8000>` (also `#rgb`, `#rrggbbaa` or a name such as `red`), `<size=40>` (in the text's own units) or `<size=150%>`, and `<br>`, nested and closed like TextMeshPro's tags. Mixed sizes share a baseline and each line is as tall as its largest text; bold is drawn twice, slightly offset, and italic slants around the baseline. Unknown tags stay as text. Demo3D's hint line uses them.
- Widgets: UI Slider (drag, whole numbers), UI Toggle (checkbox with label) and UI Input Field (click to focus, typing, Backspace, Enter to submit, caret, placeholder, character limit) and **UI Dropdown** (GameObject > UI > Dropdown). Changes call `OnUIValueChanged`, `OnUITextChanged` and `OnUISubmit` on the entity's scripts.
- **Input Field editing**: click to place the caret, drag to select, Left/Right (Ctrl: by word), Home/End, Shift to extend the selection, Backspace/Delete (Ctrl: by word), Ctrl+A/C/X/V with the system clipboard, and Tab/Shift+Tab to the next or previous field (selecting its text). Keys repeat while held, modifiers register even on quick taps, and with Num Lock off the keypad navigates. Long text scrolls to keep the caret visible. While a field has focus, gameplay scripts see no keyboard, so typing a name does not move the player.
- **Multi-line input fields** (Multi Line): Enter starts a new line and Ctrl+Enter submits; Up/Down move between lines at the same x, Home/End work per line, clicks pick the line and column, pasted text keeps its line breaks, and the field scrolls vertically to follow the caret. With **Word Wrap** (on by default) long lines wrap at the field's width, whole words first, and caret movement follows the wrapped lines.
- **Keyboard and gamepad navigation** (like Unity's EventSystem): arrow keys, the D-pad or the left stick move the selection to the nearest widget in that direction, and Enter, Space or gamepad A press it (buttons click, toggles flip, dropdowns open and their list follows Up/Down, input fields take focus); Left/Right step a selected slider, and Escape or B closes a list or leaves a text field. The selection shows a yellow outline. A mouse click selects the clicked widget but leaves navigation, so Space for jumping does not press the last button used. Scenes whose gameplay uses the arrows turn off **Keyboard Navigation** in Scene Settings > UI (Demo3D does); the gamepad always navigates. A **UI Navigation** component sets explicit links per direction (Select On Up/Down/Left/Right): in Automatic mode a set link overrides the nearest widget, Explicit follows only the links, and None keeps arrows from selecting or leaving the widget. The **Navigation** button in the Game view's bottom-right corner draws every move as an arrow (yellow: nearest widget, cyan: explicit link), like Unity's Visualize.
- The dropdown's options are a string list edited in the Inspector. Clicking it opens a list drawn over all other UI, below the box or above it when there is no room. The list highlights the hovered item, marks the selection, scrolls with the wheel past Max Visible Items, and blocks clicks to widgets underneath. Picking an item reports its index through `OnUIValueChanged`; clicking elsewhere closes it.
- UI Layout Group stacks child rects vertically or horizontally with padding and spacing, or arranges them in a **Grid** of equal cells (Cell Size, Spacing), filled left to right and top to bottom, with a fixed column count or as many columns as fit. Rows and columns also work like flexbox: **Wrap** flows children onto a new line when one is full, **Justify** places each line's children along it (Start, Center, End, Space Between), and **Align** places them across their line (Start, Center, End) when they are not stretched; a wrapping row inside a scroll view, or with a Content Size Fitter, grows downward line by line (sample: the tag chips on Demo3D's second kiosk panel). UI Scroll View clips its children and scrolls its content with the mouse wheel; a vertical or grid layout group used as content grows downward to fit its items, a horizontal one grows sideways. Views scroll **Vertical**, **Horizontal** or both: Shift + wheel scrolls sideways (the plain wheel when only Horizontal is on). While the content overflows, scrollbars on the right and bottom edges show the visible fraction; drag a handle or click a track to jump. Demo3D's settings panel is a scroll view with a Cube Color dropdown driven by the C# `ColorDropdown` script.
- The Demo3D scene has a settings panel: a slider sets the sun intensity, a toggle enables the torus's Rotator script, and a C# script greets the name typed into the input field.
- UI renders in the Game view and the Player after tonemapping, so its colors are exact. GameObject > UI creates elements and adds a Canvas automatically.
- Coordinates use a top-left origin with y pointing down, unlike Unity's bottom-left.

**Gameplay systems**
- 2D physics with **Box2D v3**: rigidbodies, box and circle colliders, triggers, collision and trigger callbacks, raycasts, `OverlapCircle`/`OverlapBox`, and **Joint 2D** (fixed, hinge with angle limits, distance).
- 3D physics with **Jolt**: rigidbodies, box, sphere and capsule colliders (any can be **Is Trigger**), collision and trigger callbacks, raycasts (`Raycast`, and `RaycastAll` for every body along the ray), `OverlapSphere`/`OverlapBox`, and **Joint** (fixed, hinge with limits, point, distance) to another body or the world; connected bodies do not collide with each other unless Enable Collision is set. Inactive objects have no collider (2D and 3D): their bodies leave the world and come back where the object is when it is activated.
- **Mesh Collider**: the exact triangles of a mesh (static and kinematic bodies) or its convex hull (dynamic bodies), from the Mesh Renderer's mesh or any mesh asset, including the built-in primitives. **Convex Decomposition** splits a concave mesh into up to Max Parts convex pieces with V-HACD, so a dynamic ring slides down a pole and a bowl holds things; it is computed once per mesh (cached) and the parts show in color while the object is selected.
- **Character Controller** (Unity-style, on Jolt's CharacterVirtual): a capsule moved by scripts with `Move(motion)` or `SimpleMove(speed)` (gravity applied; set `VerticalSpeed` to jump), that slides along walls, walks up steps (Step Offset) and slopes (Slope Limit), pushes rigidbodies and reports `IsGrounded`/`Velocity`. Raycasts and triggers see it. C#: `CharacterController.Move/SimpleMove/Jump`. Demo3D's green cube is now a character driven by the `CharacterMover` script (camera-relative WASD + Space); the torus and the glTF showcase have mesh colliders.
- **Joint motors, breakable joints and moving platforms**: hinge joints (3D and 2D) can drive toward a Motor Speed (degrees per second; positive turns the object counter-clockwise around its axis) with a maximum torque, and scripts can change it while playing. Every joint reports its reaction force and torque each step and breaks when it exceeds Break Force or Break Torque (0 = unbreakable; a hinge's own motor torque does not count). Breaking calls `OnJointBreak(force)` on the entity's C++ and C# scripts. C#: `Joint`/`Joint2D` (`UseMotor`, `MotorSpeed`, `IsBroken`, `Force`, `Torque`). **Slider** joints (3D and 2D) keep a body on a line along their Axis, optionally between limits (travel from the start position), and their motor pushes it along +Axis at Motor Speed units per second with up to Motor Max Torque newtons; the selected slider draws its travel range. Character Controllers standing on a moving body (e.g. a kinematic platform) ride along with it (Ride Moving Platforms, on by default). The sample `PlatformMover` script moves a kinematic platform back and forth; Demo3D has a moving platform and a motorized turnstile.
- **Distance joint springs**: Spring Frequency (Hz) and Damping make a Distance joint (3D and 2D) a spring toward its distance instead of a rigid rod; in 2D its motor then winches the length (Motor Speed in units per second). A 3D Distance joint with Use Motor is a **winch**: its length changes by Motor Speed per second (negative reels in), rigid or springy, and reeling in stalls while the joint pulls harder than Motor Max Torque (newtons); `CurrentLength` reports the length.
- **Physics layers**: every entity has a Layer (Inspector header). File > Project Settings names up to 32 layers and edits the layer collision matrix (2D and 3D). Queries take a layer mask; the default skips "Ignore Raycast". Joint gizmos show anchors, links and hinge axes. Demo3D has a swinging chain of point joints; Demo2D a pendulum and a hinged seesaw.
- **Vehicles**: a **Vehicle** component on a dynamic Rigidbody with a collider makes a four-wheeled car on Jolt's wheeled vehicle: wheel base, track, radius and width, suspension travel, stiffness and damping, steering angle, rear/front/all-wheel drive through differentials (or **Unpowered**: no engine, the wheels rolling freely, for trailers), engine torque and RPM with an automatic gearbox, brakes and a rear hand brake. Scripts set `Throttle` (negative reverses; against the motion it brakes first), `Steering`, `Brake` and `HandBrake`, and read `SpeedKmh`, `EngineRPM`, `Gear` and which wheels touch the ground. Optional wheel objects (e.g. cylinders) are placed and spun with the wheels, and the selected vehicle draws its wheels and suspension. `Scenes/Vehicle.scene` has a car with the `CarDriver` (WASD or a gamepad) and `ChaseCamera` scripts, ramps and crates. **Type** also offers a **Motorcycle** (two wheels on the center line with a raked front fork, kept upright and leaned into turns by Jolt's motorcycle controller; visuals in the Front/Rear Left slots) and a **Tank** (Track Wheels road wheels per side, steered by driving the tracks at different speeds, turning on the spot when standing). Center Of Mass Offset lowers the body's center of mass so vehicles stay on their wheels.
- **Soft Body**: a closed mesh on a Mesh Renderer becomes a pressurized Jolt soft body while playing. It has mass, pressure, stretch and bend compliance, damping, friction, bounciness, iterations and thickness. Its vertices are welded so seams don't split, it collides with 3D colliders, and the object follows its center. Demo3D's Soft Ball squashes as it bounces.
- **Cloth**: a **Cloth** component (with a Mesh Renderer for its material) is a sheet of Size in the object's XY plane, simulated as a Jolt soft body while playing: Resolution quads per side, pinned along its top edge or at the top corners (pinned vertices follow the object, so moving it drags the cloth), mass, stretch and bend compliance, damping, friction, iterations, thickness and a Wind acceleration. It collides with 3D colliders, renders double-sided from its simulated vertices (fresh normals every frame) and casts shadows. Demo3D has a red flag on a pole, its gusts driven by the C# `WindGust` script. With **Tear Stretch** above 0, an edge stretched past (1 + Tear Stretch) times its length breaks and the faces on it come off: a heavy curtain rips at its corners, a hard hit tears a hole (the body is rebuilt from what is left, keeping every vertex's motion). **Interpolation** (on Cloth and Soft Body, as on a Rigidbody) draws the shape between the last two physics steps, a step behind, so it moves (and motion-blurs) evenly at frame rates above the physics rate; C#: `Cloth.Interpolation`, `SoftBody.Interpolation`.
- **Cloth attached to bodies**: a Cloth's **Attach To** names a Rigidbody (a flag on a moving cart, a cape on a character): the pinned vertices follow that body, and the cloth pulls back on it at the pins with the force its weight, wind and swinging exert (smoothed and capped), so a light holder sways under a heavy banner.
- **Wind Zones** (like Unity's): **Directional** blows along the object's forward everywhere, **Spherical** outward from it, fading out at Radius; **Main** is the wind speed (m/s), stirred by **Turbulence** swirls and swelling into gusts by **Pulse Magnitude** and **Pulse Frequency**, and zones add up. The air drags rigidbodies by their size (a beach ball blows away while a crate stays put), cloth (the most), soft bodies and ropes, and particles with External Forces. The selected zone draws its arrows or reach.
- **Water Volume**: a box whose top face is a water surface. Dynamic bodies in it get Jolt's buoyancy from their submerged volume (Buoyancy 1 is neutral, above floats, below sinks), with Linear and Angular Drag in the water and a Flow velocity that carries floating things along. Cloth, soft bodies and ropes float point by point (a sheet lies on the waves, a soft ball bobs). Under water, surfaces catch drifting **Caustics** (the sunlight gathered into a web of bright lines, Caustics Scale across, fading with depth and dimming the sun), and the view through the water (from below the surface, or looking down into it) fades into **Underwater Color** murk, thicker by **Underwater Fog** per meter.
- **Waves**: a Water Volume's **Wave Height**, **Wave Length**, **Wave Direction** and **Steepness** sum three Gerstner waves (the main one and two shorter ones turned to either side) moving at deep-water speed. Bodies float on the surface under them, tilting with it and drifting with the waves' orbital motion, and with a Mesh Renderer the surface draws as a grid of Surface Resolution that follows them (in the editor too).
- **Ocean**: with **Ocean** on, a Water Volume reaches out to any distance across (buoyancy, boats and the underwater view work anywhere, Size.y deep under its surface), and its surface draws as rings of vertices around the camera, close together near it and spreading out to the camera's far plane, so the sea meets the sky at the horizon. The waves die down between 6 and 18 wave lengths away, where they would only flicker. `Scenes/Harbor.scene` is an ocean.
- **Foam**: white froth drifts on the wave crests, where the waves bunch the surface together (from the Gerstner waves' Jacobian; **Foam** sets how much, and steeper waves make more), and along shores and around anything standing in the water, where the ground is less than **Shore Foam** meters under the surface: the water shader measures it per pixel from the depth seen through the water (no rays, in the editor as well as while playing), leaving out floating things (the boxes of the dynamic bodies' meshes nearest the camera go to the shader), so the shallows foam and a drifting crate's underside does not. The foam travels to the shader in the length of the surface's normals and is broken up by drifting noise; thick foam is opaque and rough. **Contact foam** comes from the screen too, in the editor's Scene view as well as while playing: frames with water draw a depth prepass of everything else, copied where the water shader can read it, and the water foams where the view through it meets something within a quarter of Shore Foam (a shoreline, a pier post, a floating crate, a moving boat's hull), so a band of froth follows whatever touches the surface as it moves. C++: `SceneRenderTarget::GetOpaqueDepth`, `DepthCopy.frag`.
- **Ragdoll**: on a character with an Animator and a skinned Mesh Renderer, every bone at least Min Bone Length long (a fraction of the skeleton's height) becomes a capsule (Thickness of its length) and each joint a swing-twist constraint with Swing and Twist Limits; shorter bones ride along with their parent's capsule, and the Mass is shared by volume. While **Simulate** is off the capsules follow the animation as kinematic bodies (they push things and raycasts hit the character); with Simulate on it goes limp, the skeleton follows the capsules and the object follows the root one. `Physics3DWorld::AddRagdollImpulse` (C#: `Ragdoll.AddImpulse(impulse, point)`) knocks the capsule nearest a point, and limp ragdolls float in Water Volumes. The selected ragdoll draws its capsules while playing.
- **Getting up**: when a ragdoll's Simulate turns off, the animation blends in from the limp pose over **Get Up Time** instead of snapping. With **Align On Get Up**, the object first moves under the body onto the ground (found by a ray, ignoring the ragdoll) and turns along it (toward the head lying face down, toward the feet face up, turning only about the vertical), so a get-up animation starts where the body lies. C#: `Ragdoll.IsFaceUp` (to pick the animation), `GetUpTime` and `GetUpProgress`.
- **Partial ragdolls**: with **Partial Root** set to a bone's name (prefixes like `mixamorig:` ignored), Simulate makes only that bone and the bones under it go limp, hanging from capsules that keep following the animation, while the rest of the character animates on and the object stays where its animation puts it (an arm hit by a shot, a tail, a hanging limb). C#: `Ragdoll.SetPartialRoot(bone)`.
- **Breakable**: a **Breakable** object breaks into pieces when something hits it at **Break Speed** or faster along the contact normal, or when a script calls `Physics3DWorld::Break` (C#: `Breakable.Break(point)`). The pieces are Voronoi cells cut from its own mesh around seeds inside it (**Pieces**, **Seed**: the same seed breaks the same way), each cut closed with faces in the **Inside Material**; they become convex rigid bodies sharing its mass by volume, keep its velocity and spin, fly apart from the break point at up to **Explosion Speed**, and shrink away after **Debris Lifetime**. Pieces are cut once per mesh and settings and shared by every copy that breaks.
- **Impact focus**: a Breakable's **Impact Focus** puts that share of its pieces around the break point (within **Focus Radius**, a fraction of its size), so it shatters into small shards where it was hit and larger chunks farther away. Focused pieces are cut for each break, and their meshes are freed when the pieces go.
- **Destructible structures**: with **Glue Strength**, a Breakable's pieces stay stuck to the neighbours they share a cut face with, by Jolt fixed joints, and when the object was not a dynamic body its bottom pieces hold on to the ground; a joint pulled or twisted harder than Glue Strength lets go. A wall hit by a wrecking ball cracks and caves in where it is struck and the rest stands until it loses its support. Pieces of a static object weigh **Density** per m3, and whatever broke it keeps its speed into the pieces (instead of stopping against the whole object first).
- **Ropes**: a **Rope** component is a line of Segments + 1 points simulated as a Jolt soft body (stretch and bend constraints at the rope's real length, colliding by its Radius), drawn as a tube with the object's material. It hangs from the object along its -Y, or with **Attach To** spans to another object (sagging to its length: bridges, power lines); a dynamic body on the end hangs on it (a distance limit of Length from the start, plus the rope's swing pulling it), so a lamp or a wrecking ball swings from a beam. Moving the object drags the rope along; with Pin Start off the whole rope falls. A rope snaps in two (near its middle, the ends fraying) when it carries more than **Break Force** newtons (`Tension` reads its load: a hanging weight, its pull on a held body) or is pulled **Break Stretch** longer than its Length; `Physics3DWorld::SnapRope` snaps it by hand. A rope passes through the objects holding its ends.
- **Boats**: a **Boat** on a dynamic body floating in a Water Volume has an engine that pushes it forward (-Z, as vehicles) while its Propeller point is under water (none in the air), a rudder that turns it toward Turn Rate the faster it moves (a little at rest), and a keel that stops it sliding sideways. Throttle and Steering come from scripts (C#: `Boat.Throttle`, `Steering`) or WASD, arrows and the left stick with Drive With Input. `Scenes/Harbor.scene` shows water physics: drive a boat over Gerstner waves among floating crates and barrels, buoys moored to the sea bed with ropes, a floating ragdoll and a pier, under drifting clouds.
- **Towing**: a **Tow Hitch** hangs an object (a trailer, a caravan, a broken-down car) on the body **Towed By** by a ball joint between the **Hitch** point on the tower and the **Coupling** point on the object, so it follows and swings behind through turns. Clearing **Attached** unhitches it (setting it again hitches it where it stands), and a pull over **Break Force** tears it loose on its own; `CurrentForce` reads the joint's load (C#: `TowHitch.Attached`, `BreakForce`).
- **Dents**: a **Deformable** object's mesh is pushed in where it is hit faster than Min Speed, Strength centimeters per m/s over it, spread over Radius and never deeper than Max Dent in all, with fresh normals, so car bodies and cans crumple (finely divided meshes dent smoothly). A **Mesh Collider** (or convex hull) on it is rebuilt from the dented mesh, so things rest in the dents. `Physics3DWorld::Dent` dents by hand and `Repair()` undoes it.
- **Navigation mesh** (like Unity's AI Navigation): a **NavMesh Surface** bakes where agents can walk inside its box (Size, around the object) from the colliders there; moving bodies, triggers and characters are left out. Ground counts when it is no steeper than **Max Slope**, has **Agent Height** of headroom (nothing above it, under a table or inside a wall) and lies at least **Agent Radius** from any edge or wall; spots up to **Step Height** apart join up, floors stacked in one mesh each count, and areas that cannot reach each other are told apart. **Baked navigation is saved with the scene** (like Unity's NavMeshData assets): the Inspector's **Bake** (or the Navigation window's **Bake All**, the command palette's Navigation/Bake All) writes the surface's mesh to a `.navmesh` asset in a folder named after the scene (`Scenes/Navigation/NavMesh-Navigation.navmesh`, the same file on later bakes) and points its new **NavMesh Data** field at it, so play starts with it instead of baking (the Sandbox's yard: 21,882 spots; a 12,700-spot test yard bakes in 230 ms and loads in under 1 ms), and builds ship the file with the scene. A saved bake is out of date once the surface's settings or place change since (the Inspector and the Navigation window say so): play then bakes from the colliders as before, with a warning, until it is baked again; level changes are not tracked (bake again after editing the level, as in Unity). **Clear** removes the bake and its file. Surfaces without one, and Streamed ones, bake when play starts, and `NavMesh.Build()` bakes after the level changed. C++: `Navigation::SaveBaked` / `LoadSaved` / `IsSavedCurrent` / `WriteData` / `ReadData` / `SettingsKey`, `NavMeshSurfaceComponent::BakedData`, `AssetType::NavMeshData`; the selected surface draws its mesh, edges brighter.
- **Streamed navigation** (large worlds): a NavMesh Surface with **Streamed** bakes, while playing, only the tiles (**Tile Size** meters square) within **Stream Radius** of its agents and the main camera: at play start the ones around them, then a tile a frame, nearest first, as they move on, and tiles a tile farther off than the radius are dropped again, so a large field costs the raycasts and memory of the part in use. Agents repath as tiles come in. C++: `Navigation::StreamTiles`, `NavMeshSurfaceComponent::Streamed` / `TileSize` / `StreamRadius`.
- **NavMesh Agents**: a **NavMesh Agent** walks the shortest way to its destination (A* over the mesh, straightened to the corners it must turn), up to **Speed**, speeding up and braking by **Acceleration**, turning by **Angular Speed** to face the way it goes, and arriving **Stopping Distance** short (**Auto Braking** slows it in). Agents steer around each other (**Obstacle Avoidance**: of a fan of velocities around the wanted one, the nearest that runs into no one within two seconds), giving way to those with a lower **Avoidance Priority** number; a pushed-off agent finds a new way from where it is. An unreachable destination gives a **Partial** path to the nearest reachable spot. With a **Target** it keeps following that object. The selected agent draws its radius and its path. `Scenes/Navigation.scene` has six agents crossing a walled yard to their flags, two of them onto a stage (up a ramp, or jumping).
- **Agents and animation**: a NavMesh Agent's **Speed Parameter** names an Animator float it sets to its speed every frame, so a blend tree or transitions pick idle, walk or run. With **Root Motion** (and its Animator's Apply Root Motion) the animation moves it instead: the agent turns it toward its path and asks for the speed it wants there (less while it still turns), the clip's steps carry it, and each step is kept on the mesh (sliding along walls). Corners count as passed once the next is in straight sight, and scripts read **DesiredVelocity** (what it steers for) beside Velocity (how it really moves).
- **Moving surfaces**: a NavMesh Surface marked **Moving** rides on its object (a boat's deck, a lift): it is baked from that object's own colliders (moving bodies too) in the pose it has then, and other surfaces leave it out. Agents on it walk it as if it stood still (paths, avoidance and obstacles in its space; destinations ride along with it) and are carried and turned with it, after physics moved it each frame. The Scene view draws the mesh and the agents' paths where the object is now; NavMesh.SamplePosition and CalculatePath answer in world space. **Between surfaces**: an Off Mesh Link may join two surfaces' meshes (a gangway from the ground onto a boat's deck, a child of the boat so it moves with it): an agent sent to a spot on another surface walks to the link that makes the shortest way, crosses to where its far end is then, and goes on there; with no link over it gets as near as it can (a partial path).
- **Agents of any size**: the bake keeps each spot's **clearance** (how far it is from an edge or wall along the mesh), so one surface (baked for the smallest agent) serves them all: an agent goes only where there is room for its **Radius**. Through a 1.4 m door a 0.3 m agent walks straight on while a 0.9 m one goes round by the wider gap.
- **Navigation areas** (like Unity's): a **NavMesh Modifier Volume** marks the mesh inside its box as an **Area** (Walkable, Not Walkable, Road, Grass, Mud, Water, Area 6, Area 7) with a **Cost**: walking there counts that many times on paths (a road below 1 is preferred, mud above 1 is walked around when that is shorter overall), and Not Walkable takes it out of the mesh. An agent's **Area Mask** leaves areas out entirely (`NavMeshAgent.AreaMask` in C#). A volume's Cost 0 takes its area's cost from the project. The selected surface draws each area in its own color.
- **Background bakes** (like Unity's UpdateNavMesh): `NavMesh.BuildAsync()` (C++ `Navigation::BakeAsync` / `BakeAllAsync`) copies the level as it is (about 10 ms for the test yard, against 230 ms to bake it) and bakes on a worker thread from the copy's own physics while the game runs on; agents keep the old mesh until the new one is installed at the start of a later frame (`NavMesh.IsBuilding`; `Navigation::FinishBakes`). Streamed and Moving surfaces bake at once, as they follow the running scene.
- **Render-mesh geometry** (like Unity's Use Geometry): a NavMesh Surface's **Use Geometry** chooses what its bake walks on: **Physics Colliders** (as before) or **Render Meshes**: what is drawn, the Mesh Renderers' meshes, with the colliders left out (terrains count either way), so decor without colliders is ground and invisible blockers are not. The bake runs in a copy of the scene whose physics is built from those meshes (the scene itself is untouched), also for area updates; Streamed surfaces always use colliders. The choice counts toward a saved bake being up to date.
- **Agent types** (like Unity's): the project keeps a list of navigation agent types (Window > Navigation > **Agent Types**: name, radius, height, step and slope; "Humanoid" to start; saved with the project). A NavMesh Surface's **Agent Type** bakes it with that type's sizes instead of its own fields, and a NavMesh Agent's **Agent Type** makes it walk only surfaces of that type, so a yard can have one mesh for people and another, farther from the walls and off the steps, for a horse; **Any** (the default for both) keeps the surface's own settings and lets any agent use it. A type's sizes count toward a saved bake being up to date; removing a type turns its surfaces and agents to Any. C#: `NavMeshAgent.AgentTypeID`; C++: `ProjectConfig::NavAgentTypes`, `Navigation::WithAgentType` / `TypesMatch`, `Navigation::Filter::AgentType`.
- **NavMesh Modifiers** (like Unity's NavMeshModifier): a component on an object that changes how bakes treat its colliders, and its children's with **Apply To Children** (a child's own modifier wins, and a parent's without it does not reach down): **Ignore From Build** leaves them out entirely (agents neither walk on them nor go around them: a curtain, a prop that should not count), and **Override Area** makes the ground they give an **Area** with a **Cost** (a road object everywhere it is placed, mud, or Not Walkable to keep agents off a table top) without fitting a volume to it. Modifier Volumes still win where they cover it. The area travels with each surface sample, so area updates (`UpdateArea`) and saved bakes keep it (`.navmesh` format 2; format 1 files still load). C++: `NavMeshModifierComponent`.
- **Navigation window** (Window > Navigation): the scene's NavMesh Surfaces with their spot and link counts (**Bake All**, **Clear All**, or one by one), the agents (and how many are walking), the project's **Path Budget**, and the project's **areas**: their names (the Area dropdowns follow them) and default costs, saved with the project. While it is open the Scene view shows every baked navigation mesh.
- **Crowds**: agents find their neighbours through a grid of cells a few meters across and steer by the nearest ten; avoidance between agents of the same priority is reciprocal (each takes half the dodge, as in RVO), agents standing at their destination are pushed aside rather than walked around, and agents still overlapping after moving are pushed apart along the mesh. New paths (following targets, around moved obstacles, after being pushed off) are found at most **Path Budget** a frame, the others keeping to their old path until their turn; path searches reuse their per-spot state. Two groups of 100 agents swapping sides of a field walk through each other (198 of 200 at their spots after 25 s, the last two still walking, never closer than touching) in about 13 ms per update in a Debug build.
- **Generated links**: with **Generate Links**, the bake adds links of its own from every edge: drops down ledges up to **Drop Height** (one way) and jumps across gaps up to **Jump Distance** (both ways), with nothing in between, at most one per meter of edge; they cost a little more than walking the same distance, so they are used where they save a way round. A platform with no way up gets drops all round; two slabs over a pit get jumps.
- **Updating an area** while playing: `Navigation::UpdateArea(scene, min, max)` (C#: `NavMesh.UpdateArea(center, size)`) samples the ground again only in the columns over a box (one more all round) and keeps every other column's surfaces from the bake, then rebuilds the links, room, areas and generated links; agents find their place again. Knocking the yard's wall down and updating its area opens the way straight through in a quarter of a full bake's time. `Terrain::DigCrater` updates the navigation meshes over a crater by itself.
- **NavMesh Obstacles**: a box or upright capsule agents keep out of. Agents steer around one as it moves (by its velocity); with **Carve** it cuts a hole in the navigation mesh (Agent Radius wider) that paths go around, renewed when it has moved **Move Threshold**, or with **Carve Only Stationary** once it has stood still **Time To Stationary** seconds. Carving copies the baked mesh with those spots cut off (and less clearance next to the hole), so agents keep their place, and they look for new paths. A gate that closes a passage makes paths beyond it Partial; when it moves away the way opens again.
- **Off-Mesh Links**: a way between two points of the mesh that is not walked on it (a jump across a gap or onto a ledge, a ladder): **Start** and **End** in the object's space, one way or **Bidirectional**, its length counted **Cost Modifier** times. Paths go through links where that is shorter (and areas joined only by a link count as reachable); agents cross them in an arc **Arc Height** high (0 = straight) at walking speed (`NavMeshAgent.IsOnOffMeshLink` in C#). The selected link, and all links while a surface is selected, are drawn as arcs. **Handles**: a selected link's Start and End, and a selected obstacle's Center and Size (box) or Height and Radius (capsule), are handles in the Scene view (click one to move it; undoable); focusing such an object frames its handles. **Doors**: with **Agents Wait**, a link that is not Activated still carries paths, and agents walk up to it and wait (`NavMeshAgent.IsWaiting`) until it is activated, then cross; without it a closed link is no way at all. Agents coming to a closed door **queue**: those whose way goes next through it, within 8 m, line up before it nearest first, each an agent's width behind the one ahead, back the way they came, and go through one after another once it opens.
- **Wide links** (like Unity's NavMeshLink width): an Off Mesh Link's new **Width** (meters across, in the object's space; 0 = point to point) makes it a crossing along an edge (a long ledge to jump down, a row of steps): it becomes a row of crossings a couple of cells apart, and each path uses the one that suits it, so agents cross where they are instead of filing to one point (a path straight across a 6 m wide gap link is shorter than through its middle; past its end, agents come in to its edge). The Scene view draws it as a band. C#: `OffMeshLink.Width`; C++: `Navigation::LinkCrossings`.
- Audio with **miniaudio**: Audio Source with 2D or 3D spatial sound, the listener follows the primary camera. Sources can **stream** long clips (music) instead of decoding them up front, be muted, and fire overlapping `PlayOneShot` sounds. Clips can be WAV, MP3, FLAC or **Ogg Vorbis** (decoded by stb_vorbis; Demo3D's music is an Ogg file); an audio asset's Inspector shows its format, channels, rate and length. **Opus** (`.opus`) files decode through libopusfile, both as clips and streamed.
- **Gamepads**: `Input::IsGamepadButtonDown/Pressed(GamepadButton::A)` and `Input::GetGamepadAxis(GamepadAxis::LeftX)` read up to four controllers in the standard Xbox-style layout (any controller in SDL's mapping database), with a stick dead zone. C#: `Input.GetGamepadButton`, `GetGamepadButtonDown`, `GetGamepadAxis` and `GetMoveInput` (left stick or WASD/arrows). Demo3D's character walks with the left stick and jumps with A. **Rumble**: `Input::SetGamepadVibration(low, high, seconds)` (C#: `Input.SetGamepadVibration`) drives an XInput controller's heavy and light motors, for a time or until changed; it pauses with game input and stops when play stops.
- **Audio Mixer** (Window > Audio Mixer): the project's groups (Master, Music, SFX by default, plus your own) with faders in dB, mute, solo and a low-pass filter, nested under any parent group. Audio Sources pick a group in **Output**. Volumes, mute, solo and filters change live; scripts call `AudioMixer::SetVolumeDb("Music", -12)` (C#: `AudioMixer.SetVolume`). Demo3D streams a generated music loop through Music, and its settings panel has a Music Volume slider.
- **Level meters**: each mixer strip shows its post-fader level next to the fader on the same dB scale: an RMS bar (green, yellow above -12 dB, red above -3 dB), the decaying peak, and a peak hold that turns red over 0 dB. A pass-through node after each group's filter measures it on the audio thread. `AudioMixer::GetLevel(group)` returns the same values.
- **Mixer snapshots**: the Audio Mixer's Snapshots row captures every group's volume and low-pass cutoff under a name; click one to recall it, right-click to rename, overwrite or delete. Scripts blend to a snapshot over time with `AudioMixer::TransitionToSnapshot("Paused", 0.5f)` (C#: `AudioMixer.TransitionToSnapshot`), volumes linearly in dB and cutoffs in octaves. Changes the game makes to the mixer while playing in the editor (scripts, snapshots) revert on Stop.
- **Audio occlusion**: with Occlusion on, a spatial Audio Source whose line to the listener is blocked by 3D colliders (not triggers, the Ignore Raycast layer, or the source's and listener's own colliders) turns down by Occlusion Volume (dB) and is muffled by its own low-pass at Occlusion Cutoff, easing in and out over 0.15 s. `OcclusionAmount` reports it. An **Audio Occluder** component sets how much a collider blocks (thin glass 0.3, a curtain 0.15); several along the line add up, and colliders without one block fully.
- **Audio Reverb Zones**: an **Audio Reverb Zone** gives a mixer group (Master by default, or e.g. SFX) reverb while the listener is near it: full strength within Min Distance, fading out by Max Distance, with its own Room Size, Damping and Wet. Overlapping zones blend by strength, and the group's own reverb settings are what a zone fades from. The zone's spheres show when it is selected.
- **Convolution reverb**: a mixer group's FX can run its audio through an **Impulse Response** (an audio asset: the recorded or generated response of a room) with a Wet level, by uniformly partitioned FFT convolution (cost grows linearly with the response's length; about 21 ms of latency). The response is normalized to unit energy and may be mono or match the output channels. `Audio/Hall IR.wav` is a generated 2.2 s hall.
- **Microphone** input (like Unity's `Microphone`): `Microphone::Start(device, seconds, loop)` records from the default or a chosen capture device (`Devices()`) into a buffer of that length, optionally looping over it. Scripts read the `Level` (RMS over the last 50 ms) and `Peak` for voice-activated actions, the samples, and the position, and `SaveWav(path)` writes the recording as a 16-bit WAV that is imported as an audio clip (C#: the static `Microphone` class).
- **Video Player** (like Unity's VideoPlayer): video files (MP4 / H.264, MOV, WMV, AVI, MKV... whatever Windows Media Foundation reads) are **Video Clip** assets, and a **Video Player** component plays one while the scene plays: decoded on a thread of its own (a few pictures and half a second of sound ahead), the picture due now copied into a texture in place (through the frame's own commands, no waiting) and the clip's **sound played through the audio engine** (Volume, an Audio Mixer **Output** group), with the pictures following the sound's clock so they stay in step with it (without sound, real time at the Playback Speed; the speed also pitches the sound). **Render Mode** Material Override shows it on the object's UI Image, Sprite Renderer or Mesh Renderer (its own copy of its material; **Emission** makes a screen glow), **Render Texture** copies each picture into a **Target Texture** (scaled to its size, for any material, UI or camera feed to show), or API Only leaves the texture to scripts; Play On Awake, Loop and Playback Speed as in Unity. **Seeking**: setting the time jumps there (the decoder restarts at the key picture before it and only the picture at the target is shown, the sound picks up from the same moment), paused or playing, and stepping shows the next picture. C#: `VideoPlayer` with `Play` / `Pause` / `Stop`, `IsPlaying`, `IsPaused`, `IsPrepared`, `Time` (settable), `StepForward()`, `Length`, `FrameRate`, `Width` / `Height`, `FrameCount` and `Texture`, and `VideoClip` fields in scripts. C++: `VideoDecoder` (pictures as RGBA8 and sound as float samples, each from its own reader, and seeking), `Video::Play`, `SetTime`, `StepForward` and friends. Demo3D has a screen showing a test card with a beep each second (`Videos/TestCard.mp4`); clicking it pauses and plays it, and while paused Shift+click steps a picture and Ctrl+click goes back to the start (C# `VideoToggle`).
- **Voice chat**: two players talk over UDP with no server in between: each side starts a link pointed at the other (its address and port), and what its microphone picks up goes out in 20 ms **Opus** packets while it is **transmitting** (push to talk) and louder than the **voice activation** threshold, numbered so the other side notices lost ones and lets the decoder conceal them; what arrives is decoded into a short jitter buffer that the audio engine plays, at its own **volume**. A thread of its own captures, codes and sends, so it carries on across scenes and whatever the game is doing; levels of what goes out and comes in drive talking indicators. C#: `VoiceChat.Start(localPort, host, remotePort)`, `Stop`, `Transmitting`, `ActivationThreshold`, `Volume`, `LocalLevel` / `RemoteLevel`, `PacketsSent` / `Received` / `Lost` and `Submit(samples)` (generated voices). C++: `VoiceChat` (any number of links; `Options` for no microphone or no playback), `Microphone::ReadSince`. In the Sandbox's Demo3D, M starts a link to this machine's own port so you hear yourself as the other player would (C# `VoiceLoopback`).
- **Sends**: a group's FX popup can send a copy of its output (after its volume and effects) to another group at a Send Level, e.g. several groups into one return group holding a shared reverb. Sends apply live, and a send that would loop back into the group is refused.
- **Group effects**: each mixer group has an **Echo** (delay, decay, wet) and a **Reverb** (room size, damping, wet; Freeverb-style) after its filter, edited from the strip's FX button. They switch on and off and change amounts live; a new echo delay applies when play starts.
- Assets: a GUID database stored in `.meta` sidecar files, hot reload when the editor regains focus, prefabs, and scenes.
- **Import cache** (like Unity's Library folder): decoded textures (HDR included) and imported models (parsed, with generated tangents, skeletons, clips and materials) are kept in the project's `.dimension/Cache/Import`, keyed by the file's path in Assets, size, modification time and the importer version, so the next load reads them back (0.5 ms instead of 10-40 ms for the sample models). An edited file gets a fresh import; the editor drops stale entries on start, and builds ship the cache so the game skips importing.

## C# scripting

Gameplay can also be written in C#. The engine hosts the .NET runtime, as Unity hosts Mono, and C# classes appear in the Inspector's Script component next to the C++ ones.

```csharp
using System.Numerics;
using Dimension;

namespace Game
{
    public class Spinner : Behaviour
    {
        public Vector3 DegreesPerSecond = new(0, 90, 0);   // shown in the Inspector

        public override void OnUpdate(float dt) => Transform.Rotate(DegreesPerSecond * dt);
        public override void OnCollisionEnter(Entity other) => Debug.Log($"{Name} hit {other.Name}");
    }
}
```

- **Writing scripts.** Put `.cs` files in `<Project>/Scripts/`. The editor generates `GameScripts.csproj` there, so Rider or Visual Studio can open it with full IntelliSense against `Dimension.Core.dll`.
- **Reloading.** The editor watches the folder. Saving a file recompiles the scripts with `dotnet build` in about a second, shows any errors in the Console, and **hot-reloads** the assembly. The assembly loads into a collectible `AssemblyLoadContext` from memory, so the file is never locked. **While playing**, a recompile is applied at once: every live C# script keeps its serialized fields (public and `[SerializeField]`), is recreated without `OnCreate`, and gets `OnReloaded()` to rebuild the rest (other state, coroutines and event listeners start over).
- **API.** The `Behaviour` callbacks mirror the C++ ones (with `OnEnable` / `OnDisable`) (UI events are `OnValueChanged`, `OnTextChanged` and `OnSubmit`). Components available from C# are `Transform`, `Rigidbody` and `Rigidbody2D`, `MeshRenderer` and `SpriteRenderer` color, `UIText`, `UISlider`, `UIToggle`, `UIInputField`, `UIDropdown` (`Value`, `SelectedText`, `Options`), `Animator`, `ParticleSystem`, `LineRenderer` (`SetPositions`/`GetPositions`/`SetPosition`/`PositionCount`), `TrailRenderer` (`Emitting`, `Clear`), `AudioSource`, `Joint3D` (limits, spring, motor torque, break force and torque), `Vehicle` (`Throttle`, `Steering`, `Brake`, `HandBrake`, `SpeedKmh`, `EngineRPM`, `Gear`, `IsWheelGrounded`), `Cloth` (`Wind`), `SoftBody` (`Pressure`) and `NavMeshAgent` (`SetDestination`, `RemainingDistance`, `HasArrived`, `PathStatus`, `IsStopped`, `IsOnOffMeshLink`, `Warp`; and `NavMesh.SamplePosition`, `CalculatePath`, `Build`); any component's numeric Inspector fields are reachable by name too, e.g. `GetComponent("Point Light").SetFloat("Intensity", 2)` (also `GetInt`, `GetBool`, `GetVector3`, `GetVector4` and their setters). The samples `VehicleInput` (a C# car driver) and `WindGust` use them. Static helpers are `Input`, `Debug`, `Time` (`DeltaTime`, `time`, `FrameCount`), `Mathf` (Lerp, SmoothDamp, MoveTowards, PingPong, PerlinNoise, ...), `Random` (Range, Value, InsideUnitSphere, ColorHSV, ...), `Physics.Raycast` (with layer mask), `Physics.OverlapSphere`, `SceneManager`, `AudioMixer` (`SetVolume`, `GetVolume`, `TransitionToSnapshot`), `SceneManager.LoadSceneAsync`, `Entity.Find` and `Entity.Instantiate`. `Transform` adds `Forward`/`Right`/`Up`, `LocalToWorld` and `LookAt`.
- **Coroutines.** `StartCoroutine(IEnumerator)` runs until the first `yield`, then resumes after each `OnUpdate`: yield `null` (next frame), `new WaitForSeconds(s)`, `new WaitUntil(...)`, `new WaitWhile(...)`, another `IEnumerator` (runs nested) or a `Coroutine` (waits for it). Also `StopCoroutine`, `StopAllCoroutines`, `Invoke(name, delay)`, `InvokeRepeating(name, delay, rate)`, `CancelInvoke` and `Destroy(entity, delay)`. The sample `CoroutineLamp` cycles a traffic light and flashes on T.
- **C++ coroutines.** Native scripts get the same with C++20 coroutines: a member returning `Coroutine` can `co_await WaitForSeconds(s)`, `NextFrame()`, `WaitUntil(...)`, `WaitWhile(...)` or another `Coroutine` (nested); `StartCoroutine(Routine())` runs it until its first wait and ticks it after `OnUpdate`, with `StopCoroutine(id)`, `StopAllCoroutines()` and `IsCoroutineRunning(id)`. The sample `LoadSceneAfterDelay` is one.
- **Events.** Engine objects raise C# events any script can subscribe to with `+=` (and leave with `-=`), not only scripts on that entity: `UIButton.Clicked`, `ValueChanged` on `UISlider` (float), `UIToggle` (bool) and `UIDropdown` (int), `UIInputField.TextChanged`/`Submitted`, and `Entity.CollisionEnter/Exit` and `TriggerEnter/Exit`. Listeners end when play stops or the scripts reload. The sample `ButtonCounter` counts Demo3D's Spawn Ball clicks from a label.
- **Inspector fields.** Public fields of type `float`, `int`, `bool`, `string`, `Vector2/3/4`, `Color`, `Entity` the asset references `Prefab`, `Texture`, `Material`, `Mesh` and `AudioClip`, and data assets (a field of a `DataAsset` class) (picked in the Inspector or dropped from the Project window; `prefab.Instantiate(position)`, and each converts to the GUID APIs take) appear in the Inspector, as do enums (a dropdown of their names, saved as their values, so reordering the names keeps saved choices; `[Flags]` enums toggle each name in a multi-select dropdown), `[Serializable]` structs and classes of the scripts (their fields open under the field, nested up to four deep; class fields always hold an instance, as in Unity) and `List<T>` and `T[]` of any of these (a row per element with buttons to move it up or down and remove it, and + Add; saved as plain arrays; `[Range]` applies to the elements), and the values save with the scene and prefabs. Private fields with `[SerializeField]` do too, and public ones with `[System.NonSerialized]` do not.
- **Debugging.** Any .NET debugger can attach to the editor or player (Rider: Run > Attach to Process) and stop at breakpoints in script sources. **Scripts > C# Debugger** shows whether one is attached and the process id, and can open the just-in-time debugger prompt. `--wait-for-debugger` makes the editor or player wait up to 60 s for one at startup.
- **Attributes.** Fields take `[Range(min, max)]`, `[Tooltip("...")]`, `[Header("...")]` and `[HideInInspector]`; classes take `[AddComponentMenu("Category/Name")]` (listed under that category in Add Component) and `[RequireComponent(typeof(Rigidbody), ...)]` (adding the script in the editor adds those components if missing; `BoxCollider`, `SphereCollider`, `CapsuleCollider` and `MeshCollider` exist for this). The samples `Spinner` and `Launcher` use them. Fields marked `[HideInInspector]` are saved but not shown.
- **Requirements.** C# scripting needs the .NET 10 SDK at build time and the .NET 10 runtime at run time. Without them the engine builds and runs with C++ scripting only. Build copies `nethost.dll`, the `managed/` folder and the compiled scripts.

## Building

You need Windows, Visual Studio 2022 or newer with the C++ workload, and a GPU driver with Vulkan 1.3. The CMake and Ninja that ship with Visual Studio are enough. All dependencies are fetched at configure time.

**JetBrains Rider or Visual Studio:** open the folder. The IDE picks up `CMakePresets.json`; choose the `debug` or `release` preset.

**Command line.** `scripts\dev.bat` loads the MSVC environment and assumes VS 18 Community, so edit the path if yours differs.
```bat
scripts\dev.bat cmake --preset debug
scripts\dev.bat cmake --build --preset debug
scripts\dev.bat ctest --preset debug
```
Binaries land in `out/build/<preset>/bin/`.

**Validation layers (optional).** Debug builds enable `VK_LAYER_KHRONOS_validation` when it is installed, either from the Vulkan SDK or by pointing `VK_ADD_LAYER_PATH` at a self-built layer.

## Running

```bat
DimensionEditor.exe [projectDir] [--play] [--windowed]
DimensionPlayer.exe [projectDir] [--scene file.scene]
```

With no arguments, both open `Projects/Sandbox`. A built game is `<Name>.exe` next to `DimensionEngine.dll`, the game module DLL, and a `Project/` folder. ## Writing gameplay code

Scripts live in `Game/Source`, which builds `SandboxGame.dll`. The editor loads that DLL and **hot-reloads** it:

1. Edit a script in your IDE.
2. Press **Ctrl+R** in the editor (Scripts > Build & Reload), or build the `SandboxGame` target from your IDE.
3. The editor notices the new DLL within a second and reloads it. It saves the open scene to JSON, unloads the old module, loads the new one and restores the scene and selection, similar to Unity's domain reload.

Compiler errors appear in the Console, and the previous version stays loaded. A rebuild finished during Play mode is applied after you press Stop. Changes to the engine itself still need an editor restart, because the running editor holds `DimensionEngine.dll` open. The project file chooses the module by name (`"gameModule": "SandboxGame"`), and the module exports its registration function with `DIM_GAME_MODULE_ENTRY`.

Scripts are registered once and then appear in the Inspector's Script component. An entity can carry **any number of scripts**, in C++ and C# mixed. They run in the order listed, each can be enabled or disabled, and they find each other with `GetScript<T>()`. Scripts can also be added straight from Add Component. `Register<T>(name, { .Menu = "Physics/Car Driver", .Requires = { "Rigidbody", "Vehicle" } })` puts a C++ script under a category there and adds its required components.

```cpp
class Rotator : public ScriptableEntity
{
public:
    glm::vec3 DegreesPerSecond{ 0, 45, 0 };   // public field shown in the Inspector
    void OnUpdate(float dt) override { Transform().Rotation += glm::radians(DegreesPerSecond) * dt; }
};

ScriptRegistry::Register<Rotator>("Rotator").Field("Degrees Per Second", &Rotator::DegreesPerSecond);
```

The available callbacks are `OnCreate`, `OnUpdate`, `OnFixedUpdate` (60 Hz), `OnDestroy`, `OnCollisionEnter/Exit`, `OnTriggerEnter/Exit`, `OnClick` (UI Button), `OnUIValueChanged` (UI Slider, UI Toggle and UI Dropdown), `OnUITextChanged`/`OnUISubmit` (UI Input Field), and `OnAnimationEvent` (Animator state events). `GetScene().IsPointerOverUI()` tells gameplay code when the mouse is over UI. Helpers include timers (`Invoke(fn, delay)`, `InvokeRepeating(fn, delay, interval)`, `CancelInvoke`), `Time()`, `Get<T>()`, `Find(name)`, `Instantiate(prefab, pos)`, `Destroy(e)`, `Raycast(origin, dir)`, `Raycast2D(origin, dir)`, `Input::IsKeyDown`, `Physics2DWorld::*`, `Physics3DWorld::*` and `AudioWorld::Play`. Entity and asset fields such as `Entity Target;` or `.As(FieldType::Prefab)` get drag-and-drop slots.

**ECS systems** run over component sets every frame in Play mode:

```cpp
class PulseSystem : public System {
    void OnUpdate(Scene& scene, float dt) override {
        for (auto [e, tag, mesh] : scene.GetRegistry().ViewOf<TagComponent, MeshRendererComponent>()) { ... }
    }
};
SystemRegistry::Register<PulseSystem>("Pulse");
```

**New components** need a struct and a single registration. The Inspector, save/load, prefabs and Add Component menu then work automatically:

```cpp
ComponentRegistry::Register<HealthComponent>("Health", "Gameplay")
    .Field("Max", &HealthComponent::Max).Range(1, 1000)
    .Field("Tint", &HealthComponent::Tint).As(FieldType::Color4);
```

## Architecture notes

- **Modules.** The engine is a DLL that exports all of its symbols, so the editor, the player and the game module share one copy of engine state. That includes the registries, input, assets and the ImGui context. Component type ids come from a name table inside the engine, so all modules agree on them. Game modules are copied before loading, which keeps the original file free for the linker.
- **Frame flow.** Each Application layer runs `OnUpdate`, then `OnImGui`, then `OnRender` (off-screen scene targets), then `OnCompose` (swapchain blit). ImGui is drawn last, followed by present.
- **One pipeline layout.** Set 0 is the bindless `sampler2D[]`, set 1 is a dynamic UBO in the transient ring, and there are 128 bytes of push constants. Shaders are GLSL compiled to SPIR-V at build time by a glslang that is built from source, then embedded as headers.
- **Scene targets** hold HDR color, an entity-ID buffer (R32_UINT), depth (sampled by SSAO), two half-resolution AO images, a bloom mip chain, an LDR image for FXAA, and the tonemapped RGBA8 output. The editor shows the output as an ImGui image; the player blits it to the swapchain.
- **Play mode** runs `Scene::Clone()` and then `OnRuntimeStart()`, which creates Box2D/Jolt worlds, audio sources and script instances. Stop throws the clone away.
- **Assets** are referenced by GUID. `.meta` files hold the GUID and import settings, so moving or renaming in the Project panel keeps references intact.

## Roadmap toward Unity parity

Done in this milestone: everything listed under Features. These are the largest remaining areas, in a suggested order:

1. **Animation:** import of FBX models and animations (the format most character assets ship in), and a humanoid sample character in the Sandbox (to show retargeting, muscle limits and foot IK in a scene).
2. **Scripting:** Roslyn analyzers for the scripts (engine-specific warnings in the IDE and the Console, like Unity's: a misspelled callback such as `OnUpdat`, a `NativeArray` never disposed, engine calls inside jobs).
3. **AI navigation:** worlds past a surface's 4096 cells a side (tiles kept as separate meshes), and streamed tiles baked on worker threads too (no hitch as agents walk into new tiles).
4. **Effects:** a visual effect graph (nodes for spawning, updating and drawing GPU particles, edited as a graph).
5. **Platform:** Linux support (file dialogs and paths), and haptics beyond XInput rumble.
